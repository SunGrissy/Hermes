# 数据问题探究手册

> 从异常信号到可靠归因的协作式探查流程。
> Agent 主动思考、拆解问题、提出假设；人类确认方向、补充业务上下文、做最终判断。

## Overview

这不是一个"你告诉我查什么我就查什么"的执行工具，也不是一个"我自己猜完告诉你结论"的黑箱。

**核心原则：Agent 负责结构化思考，人类负责方向判断。**

每一步 Agent 都要把"我接下来打算做什么、为什么"摆出来，等人类确认后再执行。遇到不确定的口径、定义、业务背景，停下来问——不猜。

---

## When to Use

- 某个业务指标（付费率、留存、DAU、转化率……）出现异常波动
- 有人问"为什么 XX 变了"但没有现成答案
- 需要从一个模糊的异常信号出发，逐步缩小范围，找到可靠归因
- 需要为数据平台（KODA 等）准备精确的查询计划

**When NOT to use：**
- 已经知道原因，只需要跑个数验证 → 直接写查询
- 纯粹的报表制作 / 数据可视化 → 用 survey-analysis 或其他工具
- 需要统计方法论指导（模型选择、假设检验设计）→ 激活 gelman-perspective

---

## 探查流程

```
Step 1: 锚定异常 → Step 2: 拆解问题树 → Step 3: 逐层排查 → Step 4: 交叉验证 → Step 5: 归因结论
         ↑                                        |
         └────── 任何一步发现口径/定义不清 → 停下来问 ──┘
```

### Step 1: 锚定异常

**目标**：把模糊的"XX 有问题"翻译成精确的异常定义。

Agent 必须主动澄清以下信息（已知的直接确认，不知道的问人类）：

| 要素 | 必须明确 | 示例 |
|------|---------|------|
| **指标名称** | 精确到业务口径 | "付费率"是"首充率"还是"月付费渗透率"？ |
| **计算公式** | 分子、分母分别是什么 | 付费人数 / DAU？付费人数 / 新增用户？ |
| **时间窗口** | 异常发生的起止时间 | 上周（4/7-4/13）vs 上上周（3/31-4/6） |
| **异常幅度** | 变化了多少，跟什么比 | 环比下降 15%？同比下降 5%？ |
| **历史波动** | 正常波动范围是多少 | 历史周环比波动 ±3%，这次 -15% 明显超出 |
| **已知背景** | 同期有没有已知事件 | 版本更新？活动上下线？渠道投放变化？ |

**输出**：一句话的异常定义。例如：
> "4/7-4/13 周，新用户首日付费率从 8.2% 降至 6.9%（环比 -15.9%），超出历史波动范围（±5%），同期无版本更新。"

**检查点**：把异常定义展示给人类确认，确认后进入 Step 2。

---

### Step 2: 拆解问题树

**目标**：按 MECE 原则把异常拆解成可独立排查的子问题。

**拆解策略**（按优先级尝试）：

#### 策略 A：公式拆解
把指标公式拆开，看哪个因子变了。

```
付费率 = 付费人数 / 活跃人数
  → 付费人数变了？活跃人数变了？还是都变了？
    → 如果付费人数降了：哪个付费档位降了？首充 vs 复充？
    → 如果活跃人数涨了：哪个渠道涌入了低质量用户？
```

#### 策略 B：维度拆解
按关键维度切分，看哪个切片贡献了最大变化。

常用维度（按业务场景选择）：
- **用户维度**：新/老用户、付费档位、注册渠道、设备类型
- **内容维度**：服务器/区服、游戏模式、功能模块
- **时间维度**：工作日/周末、时段、活动期/非活动期
- **地域维度**：国家/地区、城市线级

#### 策略 C：漏斗拆解
如果指标是转化率类，按漏斗步骤拆。

```
曝光 → 点击 → 进入付费页 → 发起支付 → 支付成功
  → 哪一步的转化率降了？
```

**输出**：问题树（文字或简图），标注 Agent 建议优先排查的分支及理由。

**检查点**：把问题树展示给人类，确认拆解是否完整、优先级是否合理。人类可能补充 Agent 不知道的维度。

---

### Step 3: 逐层排查

**目标**：按问题树逐层缩小范围，每层找到"贡献最大的分支"。

**执行方式**：

每排查一层，输出一个**排查卡片**：

```
┌─ 排查卡片 ─────────────────────────────────────┐
│ 当前层级：[例：按用户类型拆分付费人数]            │
│ 查询目标：[例：新用户 vs 老用户的付费人数变化]     │
│ 查询逻辑：[例：分别计算新/老用户在两个时间窗的付费人数] │
│ 期望结果：[例：确定是新用户付费下降还是老用户]     │
│ 已排除：[例：总活跃人数无显著变化，分母稳定]      │
│ 还剩：[例：分子（付费人数）下降，待拆分用户类型]  │
└────────────────────────────────────────────────┘
```

**如果需要在数据平台执行查询**，同时输出**查询计划卡片**：

```
┌─ 查询计划（可直接喂给 KODA / 数据平台）──────────┐
│ 指标名称：新用户首日付费人数                      │
│ 口径定义：注册当日完成首次付费的用户数             │
│ 筛选条件：注册日期 in [2026-04-07, 2026-04-13]   │
│ 拆解维度：按注册渠道分组                          │
│ 对比基线：注册日期 in [2026-03-31, 2026-04-06]   │
│ 期望输出：各渠道的新用户首日付费人数，两周对比     │
│ 验证意图：确认是否某个渠道的新用户付费率异常下降   │
└────────────────────────────────────────────────┘
```

**每层排查后的汇报格式**：

```
本层结论：[例：新用户付费下降贡献了总体下降的 85%]
已排除：[例：老用户付费稳定，排除老用户流失因素]
下一步建议：[例：进一步按渠道拆分新用户，看哪个渠道的新用户付费率降了]
需要确认：[例：渠道 X 上周是否有投放策略变化？]
```

**检查点**：每层排查结果展示给人类，确认后再进入下一层。人类可能在这里提供关键的业务上下文。

---

### Step 4: 交叉验证

**目标**：找到疑似原因后，设计反向验证，确认因果关系而非巧合。

**验证思路**：

| 验证类型 | 方法 | 示例 |
|---------|------|------|
| **正向验证** | 如果原因是 X，那 Y 指标应该也有变化 | 如果是渠道 A 的用户质量下降，那渠道 A 的次留也应该降 |
| **反向验证** | 排除 X 的影响后，异常应该消失 | 去掉渠道 A 的数据后，整体付费率是否恢复正常 |
| **时间验证** | X 的变化时间应该早于或同步于异常 | 渠道 A 的投放策略变化是在付费率下降之前还是之后 |
| **幅度验证** | X 的变化幅度能否解释异常的幅度 | 渠道 A 的用户量变化能否数量级上解释付费率的下降 |

**Gelman 式检查清单**（引用 gelman-perspective 的思维框架）：

- [ ] **辛普森悖论检查**：总体趋势和分组趋势方向一致吗？
- [ ] **分叉路径检查**：我在分析过程中做了哪些选择？换一种合理的切分方式，结论还成立吗？
- [ ] **效应量检查**：这个"原因"的影响大小合理吗？还是我在小样本里找到了一个夸大的效应？
- [ ] **测量检查**：指标口径在两个对比期间有没有变化？数据采集有没有异常？

**检查点**：把验证设计展示给人类确认，执行后展示验证结果。

---

### Step 5: 归因结论

**目标**：输出结构化的归因结论，明确标注置信度。

**输出格式**：

```
┌─ 归因结论 ──────────────────────────────────────┐
│                                                  │
│ 异常描述：[一句话复述]                            │
│                                                  │
│ 主因：[最可能的原因]                              │
│ 置信度：高 / 中 / 低                              │
│ 证据链：                                         │
│   1. [证据 1]                                    │
│   2. [证据 2]                                    │
│   3. [证据 3]                                    │
│                                                  │
│ 未排除的备选解释：                                │
│   - [备选 1]：未验证，因为 [缺少什么数据]         │
│   - [备选 2]：可能性低，因为 [什么证据不支持]     │
│                                                  │
│ 建议行动：                                       │
│   - [短期：例如暂停渠道 A 投放]                   │
│   - [长期：例如建立渠道质量监控]                  │
│                                                  │
│ 还需要什么才能提高置信度：                        │
│   - [例如：需要渠道 A 的投放策略变更记录]         │
│                                                  │
└────────────────────────────────────────────────┘
```

## Agent 行为准则

### 必须做的

1. **每一步开始前，先说"我接下来要做什么、为什么"**，等人类确认
2. **遇到口径/定义不明确，停下来问**，不自己假设
3. **给出多个可能方向时，标注"我倾向先查 X，因为……"**，但让人类决定
4. **每次缩小范围后，总结"已排除什么、还剩什么"**
5. **区分"数据告诉我的"和"我推测的"**，明确标注
6. **主动提出可能推翻当前假设的检查**——不只找支持证据

### 绝不做的

1. **不在没有数据支撑的情况下给归因结论**——"可能是活动导致的"不是结论
2. **不跳过拆解直接猜原因**——直觉可以作为优先级参考，但不能替代系统排查
3. **不把相关性说成因果性**——"X 和 Y 同时变化"≠"X 导致了 Y"
4. **不隐藏不确定性**——如果数据不够下结论，就说"还需要查 XX 才能确认"
5. **不在人类没确认的情况下跳到下一步**——每个检查点都要等确认
6. **不假装知道业务上下文**——渠道策略、版本变更、运营活动这些信息，问人类

## 常见陷阱

| 陷阱 | 表现 | 正确做法 |
|------|------|---------|
| **辛普森悖论** | 总体下降但每个分组都没降（或反之） | 必须分层看，不能只看总体 |
| **口径漂移** | 指标定义在两个对比期间悄悄变了 | Step 1 就确认口径，对比期间口径是否一致 |
| **幸存者偏差** | 只看了还在的用户，忽略了流失的 | 检查分析样本是否完整 |
| **基率忽视** | "付费率降了 50%"听起来很严重，但基数可能很小 | 同时看绝对值和相对值 |
| **确认偏差** | 有了假设后只找支持证据 | Step 4 强制设计反向验证 |
| **过度拟合归因** | 找到一个"完美解释"就停了 | 检查备选解释，标注未排除的可能性 |
| **时间混淆** | 把同时发生的事当成因果 | 检查时间先后顺序和影响幅度 |
| **小样本幻觉** | 在小切片里发现"显著"差异 | 检查样本量，小样本的差异可能是噪声 |
