================================================================================
1. 适用场景与需求匹配
================================================================================

**核心玩法模式**  
**占位型** Master 玩法模块：在 Master 活动框架中注册一类玩法实例，使 **积分 point** 可被活动统计、任务或其它模块（如 `MasterSeasonRank`）消费；**本文件无业务逻辑**。

**典型需求场景**  
“纯积分池”活动、仅需要 point 增长与展示、作为赛季排行或其它系统的 **积分来源** 配表挂载点。

**能力标签**  
积分、框架注册、无 UI、无协议。

**与相似玩法的区别**  
- **MasterSeasonRank**：含段位、结算、红点、协议；RankPoint **仅有 Constructor + Init**，不处理排行展示。  
- 与 **Milestone** 等也不同：无领取、无 `CheckComplete` 实现。

================================================================================
2. 玩法概述
================================================================================

`MasterPlayRankPointModule` 继承 `MasterPlayModuleBase`，在 `Init` 中仅调用 `super.Init`。不监听事件、不注册推送、不维护专有字段。玩法行为完全依赖 **配表 point** 与全局 `MasterPointModule` 数据。

================================================================================
3. 玩法类型定义
================================================================================

- `MasterPlayType.RankPoint = "MasterRankPoint"`
- 模块：`MasterPlayRankPointModule` → `master_play_rank_point_module.lua`

================================================================================
4. 核心模块说明
================================================================================

- **Constructor**：空实现
- **Init**：`MasterPlayRankPointModule.super.Init(self)`，无附加逻辑
- **无** 覆写 `OnMasterPlayInfoRefresh`、`CheckComplete`、`GetRedDotKey` 等

================================================================================
5. 数据结构
================================================================================

无模块级专有缓存；玩法数据仍落在基类 `master_play_dict` 中由服务器下发的 **info/conf**，与本模块无额外解析。

================================================================================
6. 协议与接口
================================================================================

**无** 独立 `RegisterPushHandler`；协议走 Master 通用下发或其它模块。  
**无** 对外 Request 封装。

================================================================================
7. 红点系统
================================================================================

**无** `GetRedDotKey` / `InitRedDot` / `CalcRedDotNumber` 覆写；若活动入口红点需由 **其它玩法模块或入口** 实现。

================================================================================
8. 完成条件
================================================================================

**未实现** `CheckComplete`；是否完成由活动主逻辑或其它子玩法决定。

================================================================================
9. 开发注意事项
================================================================================

- 新增需求若涉及 **排行展示、领奖、任务**，应扩展专门模块或复用 `MasterSeasonRank` / `MasterMilestone` 等，而不是在本文件堆逻辑——当前设计即 **最小桩**。  
- 配表仍须正确配置 **point_id**，否则积分无法与活动关联。  
- 测试时勿因“无 Lua 逻辑”误判为未注册玩法；以 Master 活动是否挂载该 `MasterPlayType` 为准。

10. 配表结构（MasterRankPoint.xls）

### Sheet: Main

| 字段名 | 类型 | 容器 | 说明 |
|--------|------|------|------|
| id | string | - | 玩法id |
| comment | string | - | 自己看的备注 |
| tasks | AllTask | array | 本任务组包含哪些子任务，列表顺序代表默认显示顺序，引用 AllTask 子表 |
| bonuses | string | - | 活动使用的积分加成 / #R:PlayerAttr |

### Sheet: AllTask

| 字段名 | 类型 | 容器 | 说明 |
|--------|------|------|------|
| id | string | - | 任务id |
| comment | string | - | 相当于备注名，自己看的 |
| description | string | - | 任务描述（客户端） |
| task_action | string | - | 具体的任务条件类型 |
| task_filters | object | array | 过滤事件 |
| task_value | object | - | 如何累加值 |
| rewards | yield | array | 完成本任务可领的奖励，目前仅支持填写1个奖励 |
