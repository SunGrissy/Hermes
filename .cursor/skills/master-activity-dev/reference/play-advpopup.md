================================================================================
1. 适用场景与需求匹配
================================================================================

- **核心诉求**：在合适的时机触发广告（或广告占位流程），触发成功后**仅标记玩法完成**，无复杂进度。
- **典型活动**：广告位试投、一次性观看任务、极简活动占位。
- **标签**：广告、完成标记、无红点、无协议。
- **选型提示**：只需要「回调里 Request 完成」且不需要服务端进度表时选用；**最小功能模块**之一。

================================================================================
2. 玩法概述
================================================================================

模块在本地维护 `complete_cache`；业务在广告关闭或成功回调中调用 `RequestAdvComplete` 写入缓存并派发完成事件。重连时监听 `ReConnected` 做清理（`Dispose`），避免脏状态。

**流程摘要**：展示广告入口 → 用户完成观看/点击 → `RequestAdvComplete(master_play_id)` → `CheckComplete` 为真 → `MasterPlayComplete`。

**边界**：无服务端校验时，作弊风险由运营策略或 SDK 反作弊承担；若需对账必须加协议或换玩法。

================================================================================
3. 玩法类型定义
================================================================================

- **枚举**：`MasterPlayType.AdvPopup = "MasterAdvPopup"`。
- **模块类**：`MasterPlayAdvPopupModule`，继承 `MasterPlayModuleBase`。

================================================================================
4. 核心模块说明
================================================================================

- `IsRegisterPointRequired` → **false**。
- **关键方法**：`RequestAdvComplete`、`CheckComplete`。
- **事件监听**：`ReConnected` → `Dispose`。
- **事件派发**：`MasterPlayComplete`、`MasterTestCloseMainUI`。

================================================================================
5. 数据结构
================================================================================

- **complete_cache**：`[master_play_id]` → 是否已完成（布尔或标记，以实现为准）。
- 不持久化到本地存档时，杀进程后缓存丢失，活动若要求「终身一次」需服务端记录或换玩法类型。

================================================================================
6. 协议与接口
================================================================================

- **无** Register 协议；完成状态纯客户端缓存 + 业务触发，不依赖服务端 Master 下行。

================================================================================
7. 红点系统
================================================================================

- **无**；入口若需提示由外层活动或独立逻辑处理。

================================================================================
8. 完成条件
================================================================================

- `CheckComplete` 直接读取 `self.complete_cache[master_play_id]`，由 `RequestAdvComplete` 置位。

================================================================================
9. 开发注意事项
================================================================================

- 重连 `Dispose` 后缓存清空，若需与服务端对齐持久化，必须在其它模块补协议（本模块不包含）。
- 广告 SDK 回调线程与 UI 线程差异注意用主线程派发 `RequestAdvComplete`。
- 适合「一次性」任务；多段进度请换 Task/Mission 等玩法。
- `MasterTestCloseMainUI` 多用于测试或关闭主界面流程，正式环境勿依赖该事件做唯一完成反馈。
- 与激励视频失败（跳过、未就绪）的交互文案需在业务层明确，本模块只认成功回调路径。
- 同一 `master_play_id` 勿重复 `RequestAdvComplete`，除非业务允许多次完成（通常不允许）。
- 审核包体若屏蔽广告，需提供替代完成路径或活动下架，避免玩家无法 Complete。
- 与 GDPR/隐私弹窗顺序冲突时，先隐私再广告，避免 SDK 初始化失败。
- 儿童合规地区若禁止定向广告，需在业务层屏蔽本玩法入口。
- 审核截图需展示完成态时，使用测试账号或 GM 标记，勿改生产缓存逻辑。
- 冷启动首屏若需弹广告，与登录流程、强更弹窗顺序在策划案中单列一页。
- 无网环境下应有明确失败提示，勿静默不写 `complete_cache` 却显示已完成。
- 与 SDK 版本升级兼容：升级后复测 `RequestAdvComplete` 是否仍被调用。
- A/B 不同广告源时，完成判定仍以「业务回调」为准，勿绑定单一 SDK 事件名。
- 埋点：建议上报 `master_play_id`、广告位 ID、完成耗时，便于漏斗分析。
- 与激励互斥：若同屏存在其它 Master 完成条件，勿重复派发多次 `MasterPlayComplete`。
