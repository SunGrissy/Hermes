# Boss 管线文档自动审查

## 一、定位

| 层级 | 执行者 | 定位 | 耗时 |
|------|--------|------|------|
| **L0 合规检查** | 小美自己 | 机械性扫描：禁词、DoD 完整度、格式、正文终版制 | 秒级 |
| **L1 内容审查** | 独立子 agent（delegate_task） | 干净上下文语义审查：一致性、下游可执行性、盲区 | 1-2 分钟 |

**为什么分两层：**
- L0 是小美写完文档后**立即自检**的，不需要干净上下文，也不需要额外成本
- L1 需要**干净上下文**——小美和策划聊了很多轮，容易"熟视无睹"；独立 agent 只拿到终稿，用旁观者视角扫

**不拦门：** 两层审查都只输出报告，不阻止归档。是否修改由策划决定。

---

## 二、L0 合规检查（小美自审）

### 触发时机

每个阶段执行 Step 5（归档）**之前**，自动运行。

### 检查清单

#### L0-1 禁词扫描

扫描文档全文，命中任一词即标红：

```
禁词表：赌博、赌注、赌、筹码、押注、押
替代词：博弈、代价、选择、投入、风险
```

**输出：** 命中行号 + 原文 + 建议替换

#### L0-1b Boss 命名合规

检查文档中的 Boss 名称字段，扫描四条线：

1. **合规红线**——名称是否有低俗、擦边、黄赌毒联想 → 命中即标红
2. **认知门槛**——是否含典籍冷僻字、外语音译、亚文化梗等中年男性玩家不易秒懂的元素 → 标 ⚠️
3. **情绪匹配**——名字传递的情绪与文档中核心叙事/情绪内核是否一致 → 不一致标 ⚠️
4. **辨识度**——与文档中提到的同系列/已有 Boss 名称是否过于相似 → 相似标 ⚠️

#### L0-2 DoD 完整度

根据当前阶段，逐条核对必答项是否在文档中有对应内容：

| 阶段 | 必答项数 | 核对来源 |
|------|---------|---------|
| 选题/立项门 | 7-12 题（含可选项标记） | SKILL.md 阶段 1 |
| 概念门 | 11 条 + 气质对标 + 下游自检 | SKILL.md 阶段 2 |
| 方案门 | 9 题 + 对标参考 + 资源拆解表 + 流程图 | SKILL.md 阶段 3 |
| 排期/冻结门 | 6 题 + 冻结项清单 | SKILL.md 阶段 4 |
| Layout 门 | 6 题 + 冻结项对照表 | SKILL.md 阶段 5 |
| 成品上线门 | 6 题 + 风险记录 | SKILL.md 阶段 6 |

**核对方式：**
- 每条必答项在文档中搜索对应关键词/语义段落
- 有内容 → ✅
- 有标题但内容为空/占位符 → ⚠️ 标记「内容缺失」
- 整条缺失 → ❌ 标记「未覆盖」

#### L0-2b 视觉参考占位检查

扫描文档中以下位置，检查是否有图片链接或 `⬜ TBD` 占位标记：

| 位置 | 应有内容 |
|------|---------|
| 概念画面 | 概念图/气氛图链接，或 `⬜ TBD` |
| 气质对标 | 参考图/原画链接，或 `⬜ TBD` |
| 玩法流程图（方案门起） | 流程图链接，或 `⬜ TBD` |

- 有图或有 TBD 标记 → ✅
- 位置存在但既无图也无 TBD → ⚠️ 标记「缺视觉参考占位」
- 位置整体缺失 → ❌

#### L0-2c 数值二分法结构检查（仅方案门及以后）

扫描方案门文档的数值章节，检查是否按二分法显式分区：

| 检查点 | 通过标准 |
|--------|---------|
| 是否有「约束（已确认）」分区 | 标题或表格明确标注，列出体验/机制约束项 |
| 是否有「开放问题（待数值策划支持）」分区 | 标题或表格明确标注，列出留给数值策划的设计空间 |
| 约束项是否注明体验诉求 | 量级感类约束（如"最低 X 倍"）应说明对应的体验诉求（如"不亏感"） |
| 主动放弃的数值空间是否标注 | 如有"不加数值差异，纯视觉"类决策，需注明"这是体验决策"，避免数值策划加回 |

**红线检查（命中即标 ❌）：**
- 出现"期望收益 = ..."的精确计算
- 出现"RTP 估算 = X%"
- 出现"正态分布"等具体概率分布形态描述
- 约束项和开放问题混在同一张表里没有分区

#### L0-3 正文终版制检查

扫描文档正文区（变更日志区之前的部分），检查：

1. 是否存在「更新(N)」「版本N」「旧版」「废弃」等中间状态标记 → 标红
2. 变更日志区是否存在且与正文有明确分隔 → 无则提醒
3. 变更日志是否按时间倒序排列 → 乱序则提醒

#### L0-4 格式规范

1. 文档标题是否包含 Boss 名称（如「【毒后】概念门记录」）
2. 进度条是否存在且阶段标记正确
3. 下一阶段 DoR 是否已披露

### L0 输出格式

```markdown
## L0 合规检查报告

| 检查项 | 结果 | 说明 |
|--------|------|------|
| L0-1 禁词 | ✅/❌ | {命中词及位置，或"无命中"} |
| L0-2 DoD 完整度 | ✅/⚠️/❌ | {N}/{M} 项已覆盖，缺失项：{列表} |
| L0-3 正文终版制 | ✅/⚠️ | {问题描述，或"符合"} |
| L0-4 格式规范 | ✅/⚠️ | {问题描述，或"符合"} |

**结论：** PASS / {N} 项需关注
```

## 三、L1 内容审查（独立子 agent）

### 触发时机

- **方案门及以后**的阶段归档时，建议触发（概念门可选）
- 策划/小美主动说「跑一下审查」「L1 审查」时触发
- **不自动触发**——小美在归档时提示「要不要跑一下 L1 审查？」，策划说好再跑

### 调用方式

使用 `delegate_task` 派生独立子 agent，传入：
1. 当前阶段的终稿文档全文
2. 审查 prompt（见下方）
3. 上一阶段的关键结论（用于一致性比对）

**模型指定（铁律）：** L1 审查必须使用高智力模型，确保语义推理和盲区发现的质量。

```
delegate_task(
  goal="审查以下 Boss 管线文档，按审查清单逐条输出报告",
  context="<文档全文> + <上一阶段关键结论> + <审查清单>",
  toolsets=[],  # 纯推理，不需要工具
  acp_command="claude",
  acp_args=["--acp", "--stdio", "--model", "tuyoo-relay/claude-opus-4-6"]
)
```

> **为什么指定 opus：** L1 的盲区扫描和语义一致性检查质量与模型推理深度直接相关。日常对话用轻模型保持响应速度，L1 审查低频触发（每个门最多一次），用 opus 确保审查不放水。

### L1 审查清单

#### L1-1 语义一致性

跨段落/跨阶段检查，发现矛盾即标出：

| 检查维度 | 典型矛盾示例 |
|---------|-------------|
| 数值方案越界 | 方案门写了"期望收益 = 10×1200 = 12000"——这是数值策划的产出，方案门替算容易忽略关键参数（如崩塌概率）导致结果错误 |
| 核心叙事一致性 | 立项门说「暗黑霸道」，概念门变成「搞笑轻松」 |
| 情绪曲线与结构匹配 | 选了 Loop×N+Super（慢热），情绪描述却是「开场即高潮」 |
| 互动/非互动一致性 | 选了非互动型，但方案里有玩家操作选择 |
| 玩法参考与核心机制 | 说「保留核心」，但方案实现完全偏离了识别出的核心机制 |
| 记忆点与情绪轮廓 | 记忆点在终局，但情绪轮廓是「多峰均匀分布」 |

#### L1-2 下游可执行性

用四个下游视角扫描，每个视角回答「拿到这份文档能开工吗」：

| 下游 | 能开工的最低信息 | 缺了就标 ⚠️ |
|------|----------------|-------------|
| 美术 | 角色造型方向 + 气质对标 + 色调/氛围关键词 | 无气质对标、无色调方向 |
| 动画 | 关键动作描述 + 节奏意图 + 情绪强度方向 | 动作只有名字无描述、节奏无说明 |
| 特效 | 特效节点 + 视觉强度层级 + 颜色倾向 | 只写「有特效」无具体描述 |
| 程序 | 状态流转 + 交互逻辑 + 分支条件 | 分支条件模糊、状态缺失 |

#### L1-3 盲区扫描

独立 agent 基于广谱知识，主动找文档**没提到但应该想到**的问题：

1. **玩家认知负担**——规则复杂度是否超出目标用户的即时理解能力？
2. **情绪断裂风险**——有没有某个环节可能让情绪曲线断崖式下跌？
3. **同质化风险**——与已有 Boss（如果文档中提到了同系列）的差异是否足够清晰？
4. **商业化冲突**——Boss 玩法设计与配套高价物的商业化诉求是否矛盾？
5. **技术可行性信号**——有没有描述暗示了高技术风险但文档未标注的实现？

### L1 输出格式

```markdown
## L1 内容审查报告

### 语义一致性
| # | 矛盾点 | 位置A | 位置B | 严重度 |
|---|--------|-------|-------|--------|
| 1 | {描述} | {段落/条目} | {段落/条目} | 🔴高/🟡中/🟢低 |

### 下游可执行性
| 下游 | 可开工？ | 缺失项 |
|------|---------|--------|
| 美术 | ✅/⚠️ | {列表} |
| 动画 | ✅/⚠️ | {列表} |
| 特效 | ✅/⚠️ | {列表} |
| 程序 | ✅/⚠️ | {列表} |

### 盲区发现
1. {盲区描述 + 为什么值得关注 + 建议}
2. ...

### 总结
- 🔴 高优问题：{N} 个
- 🟡 建议关注：{N} 个
- 整体评价：{一句话}
```

## 四、与 boss-pipeline-guide 的集成

### 在归档 step 中的调用位置

```
Step 4（生成文档）
  ↓
Step 4.5（NEW）：L0 合规检查 → 自动执行，输出报告
  ↓ 如有 L0 问题 → 小美直接修复（禁词替换、格式修正）
  ↓
Step 4.6（NEW）：提示「要不要跑 L1 审查？」
  ↓ 策划说好 → delegate_task 执行 L1
  ↓ 策划说不用 → 跳过
  ↓
Step 5：归档（不受审查结果阻拦）
```

### L0 问题的自动修复范围

| 问题类型 | 是否自动修复 |
|---------|------------|
| 禁词命中 | ✅ 自动替换为推荐替代词 |
| 正文残留「更新(N)」标记 | ✅ 自动清理 |
| 格式缺失（标题/进度条） | ✅ 自动补全 |
| DoD 内容缺失 | ❌ 提醒策划，不自动编造 |

---

## 五、独立使用（不经过 pipeline）

当老大或策划拿着一份已有文档说「帮我审查一下」时：

1. 识别文档对应哪个阶段（从标题/内容推断）
2. 先跑 L0
3. 问是否需要 L1
4. 输出合并报告
