# Skill 编写指南

> 本 Skill 是"元 Skill"——指导 Agent 创建高质量的 Skill。借鉴 nuwa-skill 的 Agentic Protocol 和 Archon 的 Markdown Command 模式。

## 触发条件

当用户要求创建新 Skill，或 Agent 根据 `skill-evolution.mdc` 提议创建时使用。

## 局限性

- 本指南适用于 Cursor `.cursor/skills/` 体系，不适用于其他 AI 平台的 Skill 格式
- 不覆盖需要外部运行时（数据库、API 服务）的 Skill 设计
- 游戏业务类 Skill 的领域验证需要制作人参与，本指南只保证结构质量

## SKILL.md 标准模板

```markdown
# {Skill 名称}

> 一句话说明这个 Skill 做什么

## 触发条件

说明何时使用此 Skill：精确触发词 + 模糊意图描述。

## 适用场景

- 适用于：{场景列表}
- 不适用于：{场景列表}

## 工作流程（Agentic Protocol）

### Step 1: 分类（理解输入）
根据用户输入判断属于哪种子场景：
- 场景 A：{特征} → 走 Step 2a
- 场景 B：{特征} → 走 Step 2b

### Step 2: 研究（按需获取信息）
在输出结论之前，先做必要的信息收集：
- 2a. {场景 A 需要的信息和获取方式}
- 2b. {场景 B 需要的信息和获取方式}

### Step 3: 输出（结构化交付）
基于 Step 1 的分类和 Step 2 的研究结果，按以下格式输出。

## 判断框架

{核心的判断标准 / 决策树 / 评估维度}

提供的是"怎么想"而非固定答案。

## 输出格式

{模板或示例}

## 局限性

- {至少 2 条做不到什么}

## 变更记录

| 日期 | 版本 | 变更 | 来源会话 |
|------|------|------|----------|
| {date} | v1.0 | 初始创建 | Agent{code} |
```

## 编写原则

### 原则 1: Agentic Protocol（先想后答）

每个 Skill 的核心应该是一个**三步工作流**，而非一堆规则罗列：

```
分类（理解要做什么）→ 研究（需要知道什么）→ 输出（结构化交付）
```

**关键**：Step 2 的研究维度应从 Step 1 的场景分类自动推导，而不是固定清单。

**反例**：
```markdown
# 差的 Skill
## 规则
1. 做 A
2. 做 B
3. 如果 X 就做 C
4. 注意 Y
5. ...
```

**正例**：
```markdown
# 好的 Skill
## Step 1: 判断用户要什么
- 如果是新功能 → 需要了解现有架构
- 如果是修 Bug → 需要复现路径

## Step 2: 获取关键信息
- 新功能：Read 相关模块的入口文件 + Grep 类似功能的实现
- 修 Bug：Read 报错文件 + 检查最近 commit

## Step 3: 输出方案
{格式模板}
```

### 原则 2: 诚实边界（反幻觉）

必须声明做不到什么。这不是谦虚，是防止 Agent 在 Skill 能力边界外强行输出低质量结果。

**好的边界声明**：
- "本 Skill 不覆盖服务端性能优化，遇到时应建议用户使用 profiling 工具"
- "判断标准基于 Web 应用场景，移动端需要额外考虑触控交互"

**差的边界声明**：
- "可能不够完美"（太模糊）
- "AI 有局限"（废话）

### 原则 3: 可验证性

Skill 中的判断标准应尽量可验证：

| 不可验证 | 可验证 |
|----------|--------|
| "代码应该整洁" | "单个函数不超过 50 行，嵌套不超过 3 层" |
| "性能要好" | "首屏加载 < 3 秒，API 响应 < 500ms" |
| "用户体验好" | "核心操作 ≤ 3 步完成，关键信息在首屏可见" |

### 原则 4: 面向场景而非面向功能

Skill 应围绕**用户会遇到的场景**组织，而非围绕技术功能：

| 面向功能（差） | 面向场景（好） |
|----------------|----------------|
| "如何使用 FastAPI Router" | "当需要给项目添加新的 API 端点时" |
| "Playwright 测试方法" | "当需要验证前端功能是否正常工作时" |

### 原则 5: 自包含

一个 Skill 应能独立使用，不假设 Agent 已经读过其他 Skill。如果确实依赖其他 Skill，显式声明：

```markdown
## 前置依赖
- 需先阅读 `fastapi-router` Skill（了解路由约定）
```

## 质量检查清单

创建完成后，按 `skill-quality-gate.mdc` 逐项检查。快速自检：

- [ ] 有明确的触发条件？
- [ ] 有 Step 1→2→3 的三步工作流？
- [ ] 有至少 2 条诚实边界声明？
- [ ] 一个新 Agent 仅凭此文档能独立执行？
- [ ] 与现有 Skill 无重叠（或已标注边界）？
- [ ] README.md 已更新？
