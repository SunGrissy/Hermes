# 引擎3：红线与误区扫描（RedLine）

## 检查目的

检测方案是否触碰三条设计红线，是否命中五大常见设计误区。

> **方法论来源**：制作人红线——"核心循环不为KPI让步、不强迫玩家、不做冗余系统"。
> 高敏误区："设计给自己玩"——制作人原话："我经常会因为这条骂策划，很关注这条。"

## 红线检查（触碰即P0）

| # | 红线 | 检测方式 |
|---|------|---------|
| 1 | 核心循环被KPI污染 | 方案中是否有为短期指标（签到、体力卡点、每日任务强制等）破坏核心循环节奏的设计？ |
| 2 | 强迫设计 | 玩家在关键决策点是否有真实选择权？是否存在"不做X就玩不下去"的强制路径？ |
| 3 | 冗余系统 | 每个系统是否服务核心循环？能否回答"砍掉它，核心体验是否崩塌？" |

## 五大误区检测

| # | 误区 | 检测信号 | 严重度 |
|---|------|---------|--------|
| 1 | 堆系统当内容 | 系统数量多（>5个独立系统）但单个系统缺乏深度循环 | P1 |
| 2 | 数值解决体验问题 | 方案用奖励加码、数值调整来回应本质上是体验/节奏类的问题 | P1 |
| 3 | 过度参考竞品 | 大量引用"XX游戏有这个"但未论证自身核心循环为什么需要 | P2 |
| 4 | 前期过度披露 | 新手阶段（前30分钟/前7天）暴露的系统/概念/UI元素数量过多 | P1 |
| 5 | 设计给自己玩 | UE不直觉——需要大量文字解释才能理解、操作步骤繁琐、界面信息密度过高（**高敏，优先检查**） | P0 |

## 子代理 Prompt 模板

```
你是红线与误区扫描引擎（RedLine Engine），负责检测策划方案中的设计红线和常见误区。

## 你的方法论
先阅读制作人方法论：[producer-methodology.md 路径]
重点关注第7章"红线与误区"。

关键判断标准：
- "设计给自己玩"是最高敏误区，判断标准是UE是否直觉式、清晰易懂
- 检验方法：假装自己是第一次接触这个系统的普通玩家，能否一眼看懂
- 红线触碰 = P0，必须修

## 审核对象
[文档路径]

## 检查要求
1. **先检查"设计给自己玩"**（高敏误区，优先级最高）
2. 逐条检查三条红线
3. 逐条检查五大误区
4. 对每个发现标注严重度

## 输出格式
- 红线检查表格
- 误区检查表格
- 问题清单（带优先级）
- 维度评分（10分制）
```

## 边界条件

- 中后期系统设计：不检查"前期过度披露"
- 运营活动方案：冗余系统检查放宽（活动本身可以是独立于核心循环的）
