# 虚拟用户集成规范 (Virtual Player Integration)

## 概述

虚拟用户体系为 game-review 的审查流程引入**玩家行为模拟**能力——不再只靠 AI 推演"玩家可能怎么想"，而是用数据炼化出的典型用户画像，直接模拟"玩家拿到这个方案会怎么做"。

> **与 Segment 引擎的关系**：Segment 引擎做的是"静态分层影响分析"（这个设计对各群体是正面还是负面），虚拟用户做的是"动态行为模拟"（这些人拿到设计后具体会怎么玩、什么时候放弃）。前者是逻辑判断，后者是角色扮演。两者互补，不替代。

## 虚拟用户档案

### 档案来源

虚拟用户档案由独立流程创建（详见 `docs/superpowers/specs/virtual-player-creation-guide.md`），存放在 `virtual-players/` 目录下。审查引擎只消费档案，不负责创建。

### 档案结构要求

审查引擎要求每个虚拟用户档案包含以下字段（缺失则跳过该用户）：

| 字段 | 必需 | 说明 |
|------|------|------|
| 行为画像 | ✅ | 第一人称行为叙事，150-250 字 |
| 对应方法论分层 | ✅ | 四维标注（付费/活跃/社交/攻击性） |
| Prompt B（行为侧） | ✅ | 包含情境变量占位符和标准提问 |
| 元数据（聚类来源/样本量/占比） | 推荐 | 有则在报告中标注，无则标注"人工编写" |
| Prompt A（需求侧） | 仅 game-craft 使用 | 审查引擎不使用需求侧 prompt |

### 档案缺失时的降级策略

| 情况 | 处理 |
|------|------|
| `virtual-players/` 目录不存在 | 跳过虚拟用户测试，仅执行 6 大引擎，报告中标注"未启用虚拟用户" |
| 目录存在但档案 < 3 个 | 警告"虚拟用户覆盖不足"，用现有档案继续 |
| 目录存在且档案 ≥ 3 个 | 正常执行 |

## 在审查流程中的位置

```
Agent 读取方案 + 确定范围 + 选择引擎
    ↓
逐一执行 6 大引擎检查
    Purpose → Rhythm → RedLine → Value → Segment → Economy
    ↓
虚拟用户行为测试（与引擎检查串行，在 Segment 之后）   ← 新增
    ↓
汇总引擎输出 + 虚拟用户行为报告
    ↓
生成直觉层决策问题 → 交给人
```

虚拟用户测试在 Segment 引擎之后执行，因为：
1. Segment 先给出"静态分层影响"作为基线
2. 虚拟用户再用"动态行为模拟"验证或挑战 Segment 的结论
3. 如果两者矛盾（Segment 判定正面，但虚拟用户预测会放弃），自动触发 Flag 决策问题

## 执行规范

### 用户抽样

| 规则 | 说明 |
|------|------|
| 每次抽 3-4 个用户 | 从全部档案中随机抽取，不固定 |
| 必须覆盖中坚层 | 无论随机结果如何，至少包含 1 个对应"海豚/高活跃"的用户 |
| 不同轮次不固定 | game-craft 的多轮迭代中，每轮重新抽样 |

### 情境变量注入

每个用户的 Prompt B 中包含情境变量占位符，执行时从预设池中随机选一条注入。

预设情境变量池（可扩展）：

```
- "这周你刚被公会踢了，正在找新公会"
- "你这个月已经充了 2000 块，有点后悔"
- "你最近工作忙，连续三天没上线刚回来"
- "你公会刚打赢了一场服战，心情很好"
- "你最好的游戏搭档上周说不玩了"
- "你刚抽到了一个非常想要的角色，很开心"
- "游戏刚做了一次你觉得很不合理的削弱"
- "你第一次尝试充值，有点犹豫"
```

### 输出格式

```markdown
### 虚拟用户行为测试结果

**参与用户**：[用户标签1]、[用户标签2]、[用户标签3]
**数据来源**：[数据炼化版 v2 / 人工编写版]

| 用户 | 情境 | 第一反应 | 预计日活跃 | 第3天留存 | 放弃条件 | 公平感 |
|------|------|---------|-----------|----------|---------|--------|
| [标签] | [情境摘要] | [一句话] | [时间] | [是/否+原因] | [条件] | [评价] |
| ... | ... | ... | ... | ... | ... | ... |

**关键发现**：
- [与 Segment 引擎一致的发现]
- [与 Segment 引擎矛盾的发现]（如有 → 触发 Flag）
- [Segment 引擎未覆盖的发现]（虚拟用户的增量价值）

**行为模式摘要**：
- 最积极的用户：[标签] — [原因]
- 最消极的用户：[标签] — [原因]
- 最可能流失的用户：[标签] — [触发条件]
```

## 引擎裁剪规则（更新）

虚拟用户测试不是所有方案都需要：

| 方案类型 | 虚拟用户测试 | 说明 |
|----------|-------------|------|
| 完整策划案 | ✅ 必要 | 全流程测试 |
| 单系统设计 | ✅ 推荐 | 至少测中坚层反应 |
| 数值方案 | ⚠️ 可选 | 仅当涉及付费/公平时测试 |
| 活动/运营方案 | ✅ 推荐 | 活动对不同分层影响差异大 |
| UI/交互方案 | ❌ 不需要 | 虚拟用户无法评估 UI 体验 |

## 与 game-craft 的协作边界

| 场景 | game-review 中的虚拟用户 | game-craft 中的虚拟用户 |
|------|-------------------------|------------------------|
| 触发方式 | `/game.review` 或 `/game.optimize` 时自动执行 | game-craft 阶段三中由编排流程调用 |
| 使用的 Prompt | 仅 Prompt B（行为侧） | 阶段一用 Prompt A（需求侧），阶段三用 Prompt B（行为侧） |
| 隔离要求 | 无特殊隔离（审查场景没有 Design Agent） | 行为侧输出对 Design Agent 不可见 |
| 档案来源 | 同一套 `virtual-players/` 目录 | 同一套 `virtual-players/` 目录 |
