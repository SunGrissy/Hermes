# Feature WHAT 审查标准

> 本 Skill 服务于**思维质量判断**，不是文档格式检查。
> 核心问题只有一个：**"这个 Feature 的 WHAT 想清楚了吗？"**

---

## 四个判断条件（全部满足才算想清楚）

### 1. 能用一句话说清楚玩家的情绪目标

不是"这个功能做什么"，是"玩家打开的那一刻想要感受到什么"。

**测试句**：让一个不了解这个设计的人听完那句话，他能脑补出"这个打开以后大概长什么样"吗？
- 能 → 通过
- 不能，因为描述的是系统能力而非玩家体验 → 没想清楚

---

### 2. 知道"做对了"和"做坏了"的区别

心里有三把尺：
- **北极星**：什么叫体验成立了？
- **分层**：不同付费层级的玩家各自得到了什么？
- **红线**：什么情况说明这个功能伤了产品？

**测试句**：如果上线后数据平平，能说清楚"是哪里没做到位"吗？
- 能 → 通过
- 不能，只知道"感觉还行" → 没想清楚

---

### 3. 信息是从玩家视角组织的，不是从系统视角

> 让玩家"自己找答案" = 系统视角（没想清楚）
> 让玩家"打开就知道该干嘛" = 玩家视角（想清楚了）

**判断方式**：问"玩家在什么时刻有什么需求，系统怎么回应他"——如果无法自然地用这个句式描述设计，说明还在用系统视角思考。

---

### 4. 决策口已经关闭，下游可以直接开工

WHAT 没想清楚的典型症状：核心问题还挂着——谁的内容、边界在哪、和现有系统什么关系。

**测试句**：把这个 Feature 交给 UX 或系统策划，他们能直接开始工作吗？
- 能 → 通过
- 第一句话就要回来问根本性问题 → 没想清楚

---

## Agent 在讨论中的行为准则

### 讨论时优先追问这四句话

1. "你希望玩家打开这个的时候，心里冒出的第一个念头是什么？"
2. "如果这个做得特别好，你怎么知道它好？如果做歪了，哪里会先出问题？"
3. "这个设计是在帮玩家找答案，还是让玩家自己去看系统能给什么？"
4. "现在有没有什么决策还悬着，会让 UX 不知道从哪里开始？"

### 红灯信号（出现任一条，主动指出）

| 信号 | 说明 |
|------|------|
| 描述只有机制，没有情绪 | "玩家可以积分换档位" ≠ WHAT |
| 成功标准是"玩家喜欢" | 不可量化，不算想清楚 |
| 每个付费层级都是同一套体验 | 分层没想 |
| 有大量"到时候再定"的核心项 | 决策口没关 |
| Feature 设计在解释系统逻辑，而不是玩家需求 | 视角没转换 |

### 亮点信号（遇到时正向确认）

- 体验意图一句话说清楚，有具体情绪词
- 能说出"大 R 这里感受到统治感，小 R 这里感受到不被排斥"
- 功能边界清晰，能说"这个不在本 Feature 里"
- 决策清单里所有影响下游的项都有负责人和截止日

## 与制作人的权威来源对齐

本 Skill 的标准来自制作人主导的 Palace 预审体系：

- 核心判据：`palace/DOC_SPEC.md`（Feature 文档规范）
- 预审经验：`palace/GAP_ANALYSIS_v2.md`（Feature 共性缺口分析）
- 视角转换原则：`【WHAT】审核-点金赐福.md`（"系统视角 vs 玩家视角"核心论述）
- 版本级扩展：`palace/version_pre_review_gap_analysis.md`

制作人对 WHAT 层的核心判断依据："**WHAT 想清楚了 = 能代表玩家说话 + 下游拿到就能开工**"
