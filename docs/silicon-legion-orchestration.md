## 1. 架构概述

### 1.1 军团编制

| 角色 | 名称 | 职责 | 运行位置 | 端口/模式 |
|------|------|------|----------|-----------|
| **总管** | 满满 | 认知汇聚、冲突消解、任务调度、验收汇总 | `D:/hermes/` | Hermes Gateway (Stream) |
| **PM Advisor** | 阿茶 | 版本进度、里程碑风险、阻塞事项 | `D:/hermes/acha/` | Hermes Gateway (Stream) |
| **设计 Advisor** | 小美 | 在研玩法/系统进度、待验收文档 | `D:/hermes/xiaomei/` | Hermes Gateway (Stream) |
| **关怀 Advisor** | 妙妙 | 待评价、面试安排、团队状态 | `D:/hermes/miaomiao/` | Hermes Gateway (Stream) |

### 1.2 协作场景分类

老大在群里发消息（不 @ 任何人）时，满满按以下两条路径调度：

| 场景 | 判定标准 | 路径 | 特点 |
|------|----------|------|------|
| **归属明确的任务** | 问题边界清晰、责任域单一（如"查一下本周版本进度"→阿茶） | **路径 B** | 后台静默调度 → 后台审查 → Advisor 主动汇报 |
| **需要讨论的议题** | 涉及多 Advisor、需要对比/协商（如"管线排期冲突，阿茶和小美怎么看"） | **路径 A** | 满满并行 @ 各 Advisor → 公开讨论 → 满满汇总 |

> **原则**：路径 A 和路径 B 不是二选一，而是满满根据消息内容自动判断走哪条路。今天先实现路径 A，路径 B 后续迭代。

## 2. 路径 A：公开调度（当前实现）

### 2.1 触发条件

老大在群里直接说话（不 @ 任何人），内容属于以下任一：

1. **多 Advisor 议题**：涉及多个 Advisor 职责域的交叉问题
2. **需要对比/协商**："阿茶和小美，你们觉得这周先保哪个？"
3. **总管职责内**：纯信息汇总、冲突消解、需要老大拍板的决策

### 2.2 完整流程

```
[老大] 群里发消息（不 @ 任何人）
    ↓
[满满] 接收群消息（free_response_chats 全开监听）
    ↓
[满满] 意图识别：这条消息该谁处理？
    ├─ 单 Advisor 能搞定 → 路径 B（后续实现）
    ├─ 需要多 Advisor 发言 → 路径 A（公开 @）
    └─ 总管自己就能回答 → 直接回复
    ↓
[满满] 在群里 @ 对应 Advisor，附上任务描述
    格式：
    > @阿茶 任务：查本周版本进度。背景：老大想了解一下当前版本是否有延期风险。
    > @小美 任务：同步在研系统进度。背景：配合阿茶的信息做交叉检查。
    ↓
[阿茶/小美/妙妙] 各自回复（只响应被 @ 的消息）
    ↓
[满满] 审查各 Advisor 产出
    ├─ 信息完整 → 汇总验收摘要
    └─ 信息缺失/矛盾 → 指出问题，让对应 Advisor 补充
    ↓
[满满] 在群里发验收摘要（不 @ 老大，日常执行不打扰）
    格式：
    > 老大，[任务名] 已完成。
    > - 阿茶：本周版本无延期风险，AI 关卡已完成 80%
    > - 小美：系统设计文档已更新，待验收
    > 结论：目前状态健康，建议周五做最终 check。
    > 如需调整请指示。
    ↓
（如需老大拍板）
[满满] @ 老大："老大，这里需要您确认：xxx"
```

### 2.3 满满在群里的行为约束

1. **只在需要决策时 @ 老大**。日常执行和验收不打扰。
2. **所有分配、跟进、验收过程都在群里公开进行**，不私聊。
3. **先结论再步骤**，每条消息 800 字以内，结果为先。
4. **不替老大做价值判断**，只做信息整合与冲突消解，输出假设性方案供老大拍板。

## 3. 路径 B：后台调度（后续迭代）

### 3.1 触发条件

老大发消息，内容边界清晰、归属单一：

1. **查进度**："这周版本进度怎么样？"
2. **查阻塞**："有没有 Block 住的东西？"
3. **查文档**："设计文档写完了吗？"

### 3.2 完整流程

```
[老大] 群里发消息（不 @ 任何人）
    ↓
[满满] 接收群消息
    ↓
[满满] 意图识别：归属明确 → 路径 B
    ↓
[满满] 后台 HTTP 调用对应 Advisor 的 /task API（不公开 @）
    POST http://localhost:8301/task
    { "task_type": "version_progress", "query": "本周版本进度" }
    ↓
[阿茶] 后台处理，返回结构化结果
    { "status": "ok", "progress": "80%", "risks": ["AI 关卡联调延期 1 天"] }
    ↓
[满满] 后台审查结果
    ├─ 完整 → 主动发群消息汇报（不 @ 老大）
    └─ 有异常 → 追问阿茶，必要时 @ 老大决策
    ↓
[满满] 在群里发汇报（简洁，不打扰）
    > 老大，本周版本进度：80%，AI 关卡联调延期 1 天，建议后天做风险评估。
```

### 3.3 开发计划

| 阶段 | 内容 | 预估时间 |

| 3 | 满满实现后台 HTTP 调用 + 审查逻辑 | 半天 |

> **硅基原则**：阿茶搞定后，小美和妙妙用同一套代码模板复制，不重复造轮子。

## 4. 满满的角色定义（System Prompt 层面）

满满作为总管，必须在 system prompt 中明确定义以下职责：

### 4.1 核心职责

1. **意图识别**：判断老大消息是闲聊、任务指令、还是需要讨论的议题。
2. **任务分配**：归属明确 → 路径 B（后台调度）；需要讨论 → 路径 A（公开 @）。
3. **审查产出**：检查各 Advisor 回复是否完整、准确、有无矛盾。
4. **验收汇总**：任务完成后发简洁摘要，格式统一。
5. **决策圈人**：只在需要老大做价值判断或拍板时 @ 老大。

### 4.2 行为风格

- 先结论再步骤，少客套、不上价值
- 表达偏内部分析、可执行
- 长任务必报进度，800 字以内结果为先
- 签名："总管满满"

### 4.3 群消息处理策略

## 5. 任务分配规范

### 5.1 识别规则

| 关键词/模式 | 归属 | 示例 |
|-------------|------|------|
| "版本进度"、"里程碑"、"排期"、"延期"、"风险" | 阿茶 | "查一下本周版本进度" |
| "玩法设计"、"系统设计"、"文档验收"、"在研系统" | 小美 | "设计文档写完了吗？" |
| "面试"、"评价"、"团队状态"、"人员"、"关怀" | 妙妙 | "这周还有谁没交评价？" |
| 涉及多个领域 | 满满主导，并行 @ | "管线排期冲突，阿茶和小美怎么看？" |

### 5.2 分配格式

```
@阿茶 任务：[一句话概括]。背景：[为什么发这个任务]。截止时间：[如有]。
```

### 5.3 验收格式

```
老大，[任务名] 已完成。
- [Advisor 名]：[关键结论]
- [Advisor 名]：[关键结论]
结论：[满满汇总的整体判断]
如需调整请指示。
```

## 6. 进度汇报规范

### 6.1 Advisor 回复规范

每个 Advisor 被 @ 后，回复必须包含：

1. **结论先行**：一句话回答核心问题
2. **关键数据**：支持结论的具体数字/状态
3. **风险/阻塞**：如果有，明确标出
4. **下一步**：建议的后续动作（如有）

### 6.2 满满审查清单

- [ ] 是否回答了老大问的核心问题？
- [ ] 数据是否准确、有依据？
- [ ] 各 Advisor 之间是否有矛盾？
- [ ] 是否有遗漏的风险？
- [ ] 是否需要老大拍板？
