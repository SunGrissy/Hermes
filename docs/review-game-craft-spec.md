## 一、30 秒速判

**设计目的（一句话）**：用"创造者 vs 审查者"的对抗架构，让 AI 既能保护创意趣味性、又能输出逻辑严密的可交付策划案。

**宏观适配**：✅ 与现有 game-review skill 形成互补——game-review 是"事后审核已有方案"，game-craft 是"从零生成方案并内置审核"。spec 正确地让 Review Agent 复用 game-review 的 6 大引擎，避免了方法论分裂。

**核心价值判断**：这是一个值得做的方向。"创造"和"审查"的角色解耦是正确的设计直觉——单 Agent 同时负责生成和审查确实容易陷入自我验证的循环，输出趋于平庸。

### 2.3 框架解耦：Design Agent 框架 vs Review Agent 框架

| 检查项 | 结论 | 说明 |
|--------|------|------|
| 两套框架的正交性 | ✅ | Design Agent 用"核心循环/爽点/成长/包装"，Review Agent 用"Purpose/Rhythm/RedLine/Value/Segment/Economy"——视角确实不同，解耦思路正确 |
| Design Agent 框架的完备性 | ⚠️ | 只列了四个维度名称，没有任何展开。Review Agent 框架之所以有效，是因为每个引擎都有详尽的 reference 文件（检查项清单、prompt 模板、输出格式、边界条件）。Design Agent 框架目前只是四个词，无法指导实际执行（见问题 **P0-3**） |
| "核心体验目标"概念与现有 Purpose 引擎的关系 | ⚠️ | spec 说"Design Agent 负责定义核心体验目标(Hook)"、"Review Agent 的 Purpose 引擎验证机制能否支撑目的"——但现有 Purpose 引擎的检查项 #1 是"设计目的清晰度"，判断标准是"能否用一句话说清核心目的"。这和 Design Agent 的"核心体验目标"语义上高度重叠，需要明确边界，否则两个 Agent 会在同一概念上打转（见问题 P1-4） |

**维度评分**：5/10

### 2.4 Feature WHAT 审查（四条件检验）

按 Feature WHAT 审查标准，把 game-craft spec 本身当作一个"Feature"来检验——它想清楚了吗？

| 条件 | 结论 | 说明 |
|------|------|------|
| 1. 一句话说清使用者的情绪目标 | ⚠️ | spec 描述了系统做什么（"对抗迭代生成策划案"），但没有说清**使用者打开的那一刻想要什么感受**。是"我有个模糊想法，扔进去就能得到一份像样的策划案"？还是"我有初稿，想让它帮我打磨到可交付"？这两种情绪目标对应完全不同的产品形态 |
| 2. 知道"做对了"和"做坏了"的区别 | ❌ | spec 没有定义成功标准。"好的 game-craft 输出"长什么样？用什么衡量？是"输出的策划案通过了人类审核"？还是"迭代轮数少于 2 轮"？没有北极星就无法判断做没做对 |
| 3. 信息从使用者视角组织 | ⚠️ | spec 从系统架构视角描述（黑板模型、Agent 角色、对抗循环），但缺少"用户旅程"——使用者从输入到拿到交付物的实际操作步骤是什么？在哪些节点需要人类介入？每次介入大概花多长时间？ |
| 4. 决策口已关闭，下游可开工 | ❌ | 多个核心决策悬而未决（见下方 Gate 决策问题），直接拿这份 spec 去实现会在第一步就卡住 |

**维度评分**：4/10

### P1 问题（强烈建议在实现前解决）

| # | 问题 | 说明 |
|---|------|------|
| P1-1 | 阶段二与阶段三的边界模糊 | "创意大纲"和"完整策划案初稿"的区别是什么？大纲包含哪些元素、不包含哪些？如果不定义清楚，Design Agent 可能在阶段二就写出一份冗长的方案，导致阶段三变成纯润色 |
| P1-2 | 未区分使用场景 | 至少有两种截然不同的使用场景：(a) 制作人自己用——快速把脑中想法结构化 (b) 策划用——在制作人方法论框架下做方案。两种场景对 Design Agent 的"创意自由度"要求完全不同 |
| P1-3 | 对抗循环的收敛条件不够精确 | 建议改为："(a) 本轮 Review 未发现新增 Fatal（可以有遗留的 P1/P2）；且 (b) Design Agent 对每个 Fatal 要么已修复、要么已提出设计捍卫 + 妥协方案"。这样能防止"修一个冒一个"的无限循环 |
| P1-4 | "核心体验目标"与 Purpose 引擎"设计目的"概念重叠 | 建议明确分工：Design Agent 的"Hook"= 感性的体验承诺（"我要让玩家感到 X"），Purpose 引擎的"设计目的"= 理性的功能验证（"这个机制在逻辑上能实现 X 吗"）。在 spec 中用一句话说清楚 |
| P1-5 | 最终交付物格式未定义 | `draft-*.md` 和 `review-*.md` 是过程文件。最终交付给"人类终审"的是什么？是 draft 文件本身？还是一份合并后的正式文档？建议定义一个 `deliverable-[功能名].md` 作为最终产出，包含方案正文 + 审查通过记录 + 设计捍卫摘要 |

### P2 问题（建议优化）

| # | 问题 | 说明 |
|---|------|------|
| P2-1 | `draft-*.md` 和 `review-*.md` 缺少格式 schema | 建议像 game-review 的引擎 reference 一样，定义这两个文件的标准结构（必填 section、可选 section、元数据头）。否则每次生成的文件结构不一致，Review Agent 也难以稳定解析 |
| P2-2 | 与 `/game.optimize` 的边界需要明确 | `/game.optimize` = "人已经有方案，AI 帮优化"；`/game.craft` = "人只有想法，AI 从零生成"。建议在 spec 中用一句话画清边界 |
| P2-3 | "未来演进：终极形态"部分目前没有落地价值 | 作为愿景描述是好的，但建议标注为"非 MVP 范围"，避免实现时过度设计 |
| P2-4 | 缺少对"Design Agent 失败模式"的分析 | Review Agent 有制作人方法论做兜底（红线 + 误区清单），但 Design Agent 的失败模式是什么？比如：生成了一个"逻辑完美但毫无趣味"的方案怎么办？建议增加 Design Agent 的"创意质量自检"机制 |

## 四、制作人决策问题

### ~~🔒 Gate 决策 #1：对抗隔离的实现方式~~ → ✅ 已关闭

**制作人裁决**：使用本地 Gemma4 审查脚本做 Review Agent。天然物理隔离，优于所有 Cursor 内方案。

**实际执行架构**：
```
Design Agent（Cursor Claude）→ 写 draft-*.md → 本地 Gemma4 脚本读取 → 写 review-*.md → Cursor Claude 读取修复
```

### ~~🔒 Gate 决策 #2：Design Agent 框架的深度~~ → ✅ 已关闭

**制作人裁决**：轻量指导 + 案例驱动 + 先跑再补（B+C 混合）。不照搬 Review Agent 的 reference 重型体系。

### 🚩 Flag 标记 #1：阶段二的人类 Gate 是否真的必要？

**检测事实**：spec 在阶段二设置了人类确认大纲的 Gate，但在阶段四也有人类终审。如果阶段二的大纲偏了，阶段三的对抗循环本身会把问题暴露出来（Review Agent 会标记 Purpose 问题），最终在阶段四被人拦截。

**AI 判断**：阶段二的 Gate 可能是冗余的中断点，增加了用户操作成本。P2 级别。

**需要确认**：你认为阶段二的人类 Gate 是否必要？

- A) 必要——大纲方向错了，后面全白干，宁可多确认一次
- B) 不必要——让对抗循环自己发现问题，人只在最后终审
- C) 可选——默认跳过，但提供 `--confirm-outline` 参数让用户选择是否手动确认

### 💡 Sense 直觉 #1：这个 skill 的"第一个用户"是谁？

**背景**：spec 描述了一个相当复杂的系统（4 个阶段 + 2 个 Agent 角色 + 对抗循环 + 人类 Gate）。从实现复杂度看，这不是一个"周末就能搞定"的 skill。

**问题**：你设想的第一个用户和第一个使用场景是什么？这会直接决定 MVP 的裁剪范围。

## 六、建议的下一步（Gate 关闭后更新）

> Gate #1、#2 均已关闭。以下为更新后的行动建议。
> **顺序很重要**——先走查再写代码，用最低成本发现流程断点。

### 第一步：纸上走查（在写任何代码之前）

拿一个具体案例手动走完整条链路，记录每个"卡住"的地方。走查指南见 [`game-craft-walkthrough-guide.md`](game-craft-walkthrough-guide.md)。

走查会自然暴露以下问题，省去提前猜测：
- `draft-*.md` 应该长什么样（schema 从走查中长出来，而非凭空设计）
- Design Agent 的 prompt 需要多详细（走查中直接测试 prompt 效果）
- Gemma4 脚本的输入/输出格式是否匹配（走查中直接验证）
- 哪些阶段值得自动化、哪些保持手动（走查中体感判断）

### 第二步：基于走查断点修订 spec

- 在 spec 中补写"执行架构"一节（Cursor Claude → draft 文件 → Gemma4 脚本 → review 文件 → Cursor Claude 修复）
- 定义 `draft-*.md` 的 schema（从走查产出物中提炼）
- 修复走查中发现的所有流程断点

### 第三步：收集范本 + 补充 Design Agent 指导

- 收集 2-3 份好策划案范本作为 few-shot 参考
- 基于走查体验，补充 Design Agent 的 prompt 指导

### 第四步：MVP 实现

建议范围：阶段一 + 阶段三（单轮 Gemma4 审查，不循环）+ 阶段四。验证核心价值后再补多轮对抗循环。
