# 虚拟用户创建指南

> **定位**：这是一份可独立执行的任务指南。拿到这份文档的人不需要了解 game-craft 的完整架构，只需要按步骤完成"从线上数据到可用虚拟用户 Prompt"的全流程。
>
> **产出物**：一组虚拟用户档案文件（Markdown），每个文件包含一个典型用户的行为画像和两套 Prompt（需求侧 + 行为侧）。
>
> **依赖**：需要数据组（杨琳/刘洋）配合提供聚类结果。

---

## 一、目标

把线上玩家行为数据"炼化"成 5-8 个虚拟用户档案，每个档案能直接作为 LLM Prompt 使用，让 AI 以该用户的视角回答设计方案相关的问题。

**关键原则**：虚拟用户的行为特征来自数据聚类，不来自人工拍脑袋。我们信任数据涌现出的自然分群，而非预设"应该有几种玩家"。

---

## 二、全流程概览

```
Step 1: 定义行为特征维度
Step 2: 数据提取与清洗（数据组执行）
Step 3: 聚类分群（数据组执行）
Step 4: 聚类结果验收（制作人 + 数据组）
Step 5: 行为叙事化（制作人或 Agent 执行）
Step 6: Prompt 封装（制作人或 Agent 执行）
Step 7: 效果验证
```

---

### Step 1：定义行为特征维度

从以下维度表中选取与当前产品相关的特征。不需要全选，根据产品类型裁剪。

## 输出要求

1. 每个用户一行，每个特征一列的宽表（CSV）
2. 附一份特征分布描述（各特征的 min/max/median/mean/std）

### Step 2：数据提取与清洗

**负责人**：数据组（杨琳/刘洋）

**输入**：Step 1 的特征选取清单

**操作**：
1. 按清单从数据仓库提取特征宽表
2. 处理缺失值（未充值用户的付费特征 = 0，未加入公会的社交特征 = 0）
3. 标准化（Z-score 或 Min-Max，聚类前必须做）
4. 输出 CSV + 特征分布描述

**产出**：`player_features_[产品名]_[日期].csv`

**注意**：
- 数据时间范围建议最近 3 个月的稳定期，避开大版本更新和春节/暑期等异常高峰
- 数据组不需要知道这些数据最终用来做什么，只需按清单提取即可

---

### Step 3：聚类分群

**负责人**：数据组 或 制作人（如果有 Python 环境）

**输入**：Step 2 的标准化特征宽表

**操作**：

1. **选算法**：推荐 K-Means（简单可解释）。如果怀疑数据有非球形分布，可试 DBSCAN 或 GMM

2. **确定最优 K 值**：
   ```python
   # 跑 K=3 到 K=10，画轮廓系数曲线
   from sklearn.cluster import KMeans
   from sklearn.metrics import silhouette_score

   scores = {}
   for k in range(3, 11):
       model = KMeans(n_clusters=k, random_state=42, n_init=10)
       labels = model.fit_predict(X)
       scores[k] = silhouette_score(X, labels)

   # 取轮廓系数最高的 K，如果多个 K 接近，选较小的（奥卡姆剃刀）
   ```

3. **输出每个聚类的特征中心**：
   ```python
   # 反标准化后的聚类中心，让数值有业务含义
   centers = pd.DataFrame(
       scaler.inverse_transform(model.cluster_centers_),
       columns=feature_names
   )
   centers['cluster_size'] = pd.Series(labels).value_counts().sort_index().values
   centers['cluster_pct'] = centers['cluster_size'] / len(labels) * 100
   ```

4. **为每个聚类贴标签**：基于特征中心的数值，用一个短语概括（如"社交海豚""沉默大R""休闲白嫖"）

**产出**：

```markdown
# 聚类结果摘要

**算法**：K-Means, K=6, 轮廓系数=0.42
**样本量**：58,320 名活跃用户

| 聚类 | 标签 | 占比 | 月均充值 | 日均在线 | 社交发起率 | PVP参与率 | 关键特征 |
|------|------|------|---------|---------|-----------|----------|---------|
| 0 | 沉默大R | 8% | ¥2,100 | 95min | 12% | 35% | 高付费低社交 |
| 1 | 社交海豚 | 23% | ¥350 | 45min | 68% | 60% | 中付费高社交 |
| 2 | 活跃白嫖 | 31% | ¥0 | 55min | 45% | 70% | 零付费高活跃 |
| 3 | 佛系散人 | 18% | ¥30 | 20min | 8% | 15% | 低付费低活跃 |
| 4 | PVP猎手 | 12% | ¥800 | 70min | 30% | 95% | 高攻击性 |
| 5 | 周末战士 | 8% | ¥150 | 15min平日/90min周末 | 55% | 50% | 工作日几乎不上 |
```

### Step 4：聚类结果验收

**负责人**：制作人

**验收标准**：

- [ ] **数量合理**：5-8 个聚类。少于 5 个太粗，多于 8 个难以管理
- [ ] **各群有区分度**：任意两个聚类之间至少有 2 个维度存在显著差异
- [ ] **覆盖中坚层**：必须有一个聚类对应制作人方法论中的"中坚层"（海豚 + 高活跃 + 强社交 + 中攻击性）。如果没有，检查特征选取是否遗漏了关键维度
- [ ] **没有"垃圾桶群"**：不应有一个聚类占比 > 40% 且特征无明显特点（说明 K 值太小或特征区分度不够）
- [ ] **与直觉大致吻合**：聚类结果不需要和你预想的完全一样（数据涌现的分群往往有惊喜），但不应完全反直觉

**不通过时**：
- 回 Step 1 调整特征维度，或回 Step 3 调整 K 值
- 如果反复不通过，可能说明当前产品的用户行为确实没有清晰的分群结构——这本身就是一个有价值的发现

### Step 5：行为叙事化

**负责人**：制作人 或 Agent（可以让 Claude 辅助）

**输入**：Step 3 的聚类结果摘要

**操作**：对每个聚类，把统计特征转写为**第一人称的行为叙事**。

**转写原则**：
1. **用行为描述，不用数字**："我每天晚上 9 点上线"而非"日均在线 45 分钟"
2. **用情感动机，不用标签**："碰到喜欢的皮肤会充点钱"而非"中付费用户"
3. **包含决策模式**：这个人在游戏里做决定的方式是什么？冲动型？精打细算？从众？
4. **包含流失敏感点**：什么情况下这个人会不玩了？
5. **字数 150-250 字**：太短缺乏细节，太长 prompt 过长

**示例**：

```
聚类 1（社交海豚）的统计特征：
- 月充值 ¥200-500，首充在第 3 天
- 日均在线 45min，集中在 21:00-23:00
- 公会活跃度 Top 20%，日均聊天 15 条
- PVP 参与率 60%，只打同战力段
- 流失前信号：公会成员减少 → 自己活跃度下降 → 停止付费 → 流失
```

**转写结果**：

```
我是个上班族，每天晚上 9 点到 11 点是我的游戏时间。不算重度玩家，
但只要上线就会认真玩。我在公会里挺活跃的，喜欢和固定的几个人一起打，
聊天也多，有时候上线主要就是来聊天的。

花钱方面不算大手笔，但也不白嫖——碰到喜欢的皮肤或者公会战要冲一波的
时候会充点。第一次充值是刚玩第三天，觉得这游戏能长期玩就充了。

PVP 我打，但只打差不多强的人，碾压别人没意思，被碾压更烦。
我比较在意公平，如果感觉花钱就是一切，我会不舒服。

最容易让我流失的情况是公会的人慢慢不上了。一旦我常组队的那几个人
不玩了，我自己也会逐渐失去动力。先是不充钱了，然后登录变少，
最后就不玩了。这个过程大概两到三周。
```

**产出**：每个聚类一段行为叙事文本。

### Step 6：Prompt 封装

**负责人**：制作人 或 Agent

**输入**：Step 5 的行为叙事

**操作**：为每个虚拟用户生成一份档案文件，包含元数据 + 行为叙事 + 两套 Prompt。

**档案文件模板**：

```markdown
# 虚拟用户档案：[标签名]

## 元数据
- **聚类编号**：[N]
- **数据来源**：[产品名] 活跃用户聚类，样本量 [X] 人，占活跃用户 [Y]%
- **数据时间**：[起止日期]
- **对应制作人方法论分层**：
  - 付费能力：[鲸鱼/海豚/免费]
  - 在线活跃：[高/中/低]
  - 社交参与度：[强/中/弱]
  - 社交攻击性：[强/中/弱]

## 行为画像

[Step 5 的行为叙事，原文粘贴]

## 决策模式摘要
- **付费决策**：[一句话，如"社交场景驱动，不冲动消费"]
- **留存驱动**：[一句话，如"社交关系 > 内容消耗"]
- **流失敏感点**：[一句话，如"公会生态恶化"]

## Prompt A：需求侧（用于 Design 阶段）

> 以下 prompt 用于阶段一"信息收集"，由 Design Agent 调用。
> 目的：了解这类玩家的期待和欲望。

你是一个游戏玩家，你的行为特征如下：

[行为画像全文]

现在，游戏要新增一个功能。在你还不知道具体内容的情况下，请回答：
1. 你在游戏里最期待获得什么样的新体验？
2. 什么样的新功能会让你更愿意每天上线？
3. 你最不希望新功能带来什么？（比如打破了什么你在意的东西）

请以第一人称回答，用你平时的口吻，不需要面面俱到，说最真实的想法。

## Prompt B：行为侧（用于 Review 阶段）

> 以下 prompt 用于阶段三"行为侧测试"，由 Gemma4 脚本调用。
> 目的：模拟这类玩家面对具体方案时的真实行为。
> **Design Agent 不可见此 prompt 及其输出。**

你是一个游戏玩家，你的行为特征如下：

[行为画像全文]

[情境变量占位符——每次调用时随机填入一条，如：
  "这周你刚被公会踢了，正在找新公会" /
  "你这个月已经充了 1500 块，有点后悔" /
  "你最近工作忙，连续三天没上线刚回来" /
  "你公会刚打赢了一场服战，心情很好"]

现在请阅读以下游戏设计方案：

---
[此处插入 draft-[功能名].md 的内容]
---

请以第一人称回答：
1. 看完这个方案，你的第一反应是什么？（一句话）
2. 如果这个功能上线了，你周一到周五每天会花多少时间在上面？
3. 第三天你还会玩这个功能吗？为什么？
4. 什么情况下你会因为这个功能而不想玩这个游戏了？
5. 你觉得这个功能对花钱多的人和不花钱的人公平吗？

请以你平时的口吻回答，说真话，不需要客气。
```

### Step 7：效果验证

**负责人**：制作人

在正式用于 game-craft 流程之前，先做一次快速验证。

**验证方法**：选一个你已经有判断的设计方案（已上线的、你知道效果好坏的），把它喂给虚拟用户的行为侧 Prompt，看输出是否和真实数据/你的判断一致。

**验证清单**：

| 验证项 | 方法 | 通过标准 |
|--------|------|---------|
| 需求侧输出是否像真人说话 | 读 Prompt A 的输出 | 不像 AI 在列 bullet points，像一个人在聊天 |
| 不同用户的需求是否有差异 | 对比 5-8 个用户的 Prompt A 输出 | 至少 3 对用户在核心诉求上有明显不同 |
| 行为侧是否能发现真实问题 | 用一个有已知缺陷的方案测试 Prompt B | 至少有 2 个用户指出了你已知的那个缺陷 |
| 情境变量是否影响输出 | 同一用户 + 同一方案，换不同情境变量各跑一次 | 输出有可感知的差异（不是模板化的换词） |
| 大R和免费用户的反应是否合理分化 | 用一个明显偏付费的方案测试 | 大R 反应正面，免费玩家反应负面或冷淡 |

**不通过时**：
- 输出像 AI 说教 → 调整行为叙事的口吻，加入更多口语化表达
- 不同用户输出雷同 → 行为画像的差异化不够，回 Step 5 加强差异点
- 行为侧发现不了已知问题 → Prompt B 的提问方式需要调整，问题太泛或太引导
- 情境变量无效 → 情境描述太弱，改为更具冲击力的场景

## 四、维护与更新

### 更新频率

| 触发条件 | 操作 |
|---------|------|
| 每季度（常规） | 用最新 3 个月数据重跑 Step 2-6 |
| 大版本更新后 | 用更新后 1 个月的数据重跑，观察分群是否发生结构性变化 |
| 虚拟用户在走查/实际使用中表现不佳 | 回溯定位问题环节（特征不够？聚类太粗？叙事失真？），针对性修复 |

## 五、常见问题

**Q：我们产品的数据量不够大怎么办？**
A：聚类对样本量的要求不高，1000+ 活跃用户就能跑出有意义的分群。但如果某些特征（如 PVP、公会）的参与率很低，那些维度的区分度会不够——这时候删掉这些维度、用剩余维度聚类，反而更干净。

**Q：数据组说没有某个特征的埋点怎么办？**
A：删掉那个特征，不要用估算值代替。宁可少几个维度，也不要用假数据。聚类结果的可信度取决于最弱的那个特征。

**Q：聚类结果和制作人方法论的四维分层对不上怎么办？**
A：这是正常的，而且是好事。四维分层是理论模型，聚类是数据事实。如果数据告诉你实际存在 7 种行为模式而方法论只定义了 5 种，说明方法论需要更新，而不是数据错了。在档案的"对应方法论分层"字段里，如实标注最接近的映射即可，不需要强行对齐。

**Q：能不能不用数据，先手动写几个虚拟用户跑通流程？**
A：**可以，但必须标注为"人工编写版"**，并在效果验证中严格测试。走查阶段用人工版是合理的（快速验证流程），但正式使用前必须替换为数据版。人工编写的用户画像最大的问题是"策划以为玩家怎么想"而非"玩家真的怎么做"——这恰恰是虚拟用户体系要解决的问题。
