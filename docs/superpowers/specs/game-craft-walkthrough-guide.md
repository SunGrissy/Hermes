# Game Craft 纸上走查指南

> **目的**：在写任何代码之前，用一个真实案例把整条链路手动走一遍，记录每个"卡住"的地方，反哺 spec 修订。
>
> **原则**：走查不是测试——不追求"走通"，而是追求"走出所有走不通的地方"。每一处卡顿都是 spec 的缺口。

---

## 一、准备工作（走查前一天完成）

### 1.1 选案例

选一个**你脑子里已经有模糊想法、但还没写过正式文档**的案例。要求：

- [ ] 复杂度适中：不能太简单（"做个签到"没什么好走的），也不能太复杂（完整赛季系统走不完）
- [ ] 你自己有判断力：走到"这个好不好玩"的决策点时，你能凭直觉给出答案
- [ ] 最好涉及经济/成长/社交中的至少一个——这样 Gemma4 的 6 大引擎才有东西可查

**推荐案例**："钓鱼小游戏"（spec 中提到的例子）、"Boss 挑战赛"、"赛季通行证"、"公会远征"。

选定后写下来：

```
走查案例：________________
一句话描述：________________（模拟用户的原始输入）
```

### 1.2 准备工具

| 工具 | 用途 | 检查项 |
|------|------|--------|
| Cursor + Claude 会话 | 扮演 Design Agent | [ ] 能正常对话 |
| 本地 Gemma4 审查脚本 | 扮演 Review Agent | [ ] 脚本能跑通、能读取指定路径的 md 文件、能输出 review 结果 |
| 虚拟用户档案 | 扮演典型玩家 | [ ] 至少准备 3 个虚拟用户档案（见 1.5 节） |
| 一个空的工作目录 | 放黑板文件 | [ ] 建好目录，如 `walkthrough/fishing-game/` |
| 计时器 | 记录每个阶段耗时 | [ ] 手机计时器即可 |
| 走查记录表 | 记录断点 | [ ] 打印或用 Notion 打开下方的记录表模板 |

### 1.3 准备 Gemma4 脚本的输入格式

在走查之前，先确认一个关键问题：

- [ ] Gemma4 脚本期望的输入文件格式是什么？（纯 Markdown？需要特定 section？需要 YAML 头？）
- [ ] 脚本的输出写到哪里？（同目录下的 `review-*.md`？stdout？）
- [ ] 脚本需要哪些参数？（文件路径？引擎选择？）

**如果这一步就卡住了——恭喜，这就是走查的第一个发现：spec 没有定义 `draft-*.md` 的 schema。**

### 1.4 给 Design Agent 的 System Prompt 草稿

走查时你需要在 Cursor 里用一段 prompt 把 Claude "变成" Design Agent。提前写好这段 prompt：

```markdown
你现在是 Game Craft 的 Design Agent（创造者角色）。

你的目标是帮用户把一个粗略的游戏设计想法，发展成一份结构化的策划案草稿。

你的工作框架有四个维度：
- 核心循环 (Core Loop)：玩家反复做的事是什么？每次循环的压力和释放在哪里？
- 爽点/心流 (Hook/Flow)：玩家最爽的瞬间是什么？用什么机制制造这个瞬间？
- 成长/驱动力 (Progression)：玩家为什么要继续玩？短/中/长期目标各是什么？
- 包装/情境 (Context)：这套机制包在什么情境里？什么主题/叙事让它更有代入感？

你的工作分两步：
1. 先通过提问收集信息，理解用户想要的核心体验
2. 再输出一份创意大纲，写入 draft-[功能名].md

注意：你是创造者，你的优化目标是"好玩、心流、爽感"。不要自我审查、不要过早考虑风险。
```

- [ ] 准备好这段 prompt（可以根据案例微调）

### 1.5 准备虚拟用户档案

走查需要虚拟用户参与"需求侧访谈"和"行为侧测试"。准备方式分两种：

**方式 A：已有数据炼化版（推荐）**

如果已按 [`virtual-player-creation-guide.md`](virtual-player-creation-guide.md) 完成了虚拟用户创建，直接使用 `virtual-players/` 目录下的档案文件。

- [ ] 至少选 3 个差异化明显的用户（如：大 R + 社交海豚 + 活跃白嫖）
- [ ] 确认每个档案的 Prompt A（需求侧）和 Prompt B（行为侧）都完整

**方式 B：人工速写版（走查专用，后续必须替换）**

如果还没有数据版，可以先手写 3 个临时用户画像用于走查。但**必须标注为"人工编写版"**。

快速模板（每个用户 5 分钟内写完）：

```markdown
## 临时虚拟用户：[昵称]（人工编写版，仅供走查）

**画像**：[3-5 句话描述这个人的游戏行为和偏好]

**Prompt A（需求侧）**：你是一个游戏玩家：[画像]。
游戏要新增一个功能，在你还不知道具体内容的情况下：
你最期待什么新体验？什么会让你更愿意上线？最不希望什么被改变？

**Prompt B（行为侧）**：你是一个游戏玩家：[画像]。
[随机情境：最近公会活动很多/最近比较忙只能碎片上线/刚充了一笔钱]。
请阅读以下设计方案：[插入 draft]。
你的第一反应是什么？这周你会怎么玩？第三天还会玩吗？什么时候会放弃？
```

建议写的 3 个用户：
1. 一个中重度付费 + 社交活跃的（对标中坚层）
2. 一个零付费 + 高活跃的（最挑剔的白嫖玩家）
3. 一个重度付费 + 低社交的（大 R 视角）

- [ ] 3 个临时用户已写好，Prompt A/B 各就位
- [ ] 标注了"人工编写版，仅供走查"

### 1.6 准备情境变量池

行为侧测试需要给每个虚拟用户注入一条随机情境。提前准备 6-8 条：

```
- "这周你刚被公会踢了，正在找新公会"
- "你这个月已经充了 2000 块，有点后悔"
- "你最近工作忙，连续三天没上线刚回来"
- "你公会刚打赢了一场服战，心情很好"
- "你最好的游戏搭档上周说不玩了"
- "你刚抽到了一个非常想要的角色，很开心"
- "游戏刚做了一次你觉得很不合理的削弱"
- "你第一次尝试充值，有点犹豫"
```

- [ ] 准备了至少 6 条情境变量

## 二、执行步骤

### 阶段一：信息收集（目标 15-20 分钟）

**操作**：
1. 开一个 Cursor 会话，贴入 Design Agent 的 system prompt
2. 用你选的案例作为第一句输入（如："我想做一个钓鱼小游戏"）
3. 让 Claude 提问，你作为"有想法的制作人"来回答
4. 当 Claude 提炼出"核心体验目标"时，进入虚拟用户需求侧访谈

**操作（虚拟用户需求侧访谈）**：
5. 取出准备好的 3 个虚拟用户的 Prompt A（需求侧）
6. 在 Cursor 里逐个运行：贴入 Prompt A，把 Claude 的回答记录下来
7. 把 3 个虚拟用户的需求侧回答汇总到 `walkthrough/[案例名]/player-desires-[功能名].md`
8. 把这份文件交给 Design Agent（Cursor Claude），告诉它："这是典型玩家的需求调研，参考这些来理解玩家期待"

**走查记录**：

| 记录项 | 内容 |
|--------|------|
| 实际耗时 | ___ 分钟（制作人对话 ___min + 虚拟用户访谈 ___min） |
| Claude 问了几个问题 | ___ 个 |
| 问题质量（1-5） | ___（1=全是废话，5=每个都戳到点上） |
| 核心体验目标的提炼质量（1-5） | ___（1=空话套话，5=一句话就让人"看到"这个游戏） |
| 虚拟用户需求侧回答是否有差异 | 差异大/差异小/几乎一样 |
| 需求侧回答对 Design Agent 有帮助吗 | 有（举例）/ 没有（为什么） |
| **卡住的地方** | 自由记录 |
| **意外发现** | 自由记录 |

**重点观察**：
- Claude 是否抓住了"体验"而非"机制"？（如果它问的全是"有几种鱼""升级多少级"，说明 prompt 不够好）
- 提炼出的核心体验目标，你自己认不认？（不认 = prompt 需要调整）
- **虚拟用户的需求侧回答是否像真人？** 如果像 AI 在列 bullet points 而不是一个人在聊天 → Prompt A 的口吻需要调整
- **不同虚拟用户的回答是否有区分度？** 如果大 R 和白嫖玩家说的话差不多 → 行为画像的差异化不够

---

### 阶段二：创意大纲（目标 10-15 分钟）

**操作**：
1. 让 Claude 基于核心体验目标，输出创意大纲
2. 要求它按四个维度（核心循环/爽点/成长/包装）组织
3. 把输出复制到 `walkthrough/[案例名]/draft-[功能名].md`

**走查记录**：

| 记录项 | 内容 |
|--------|------|
| 实际耗时 | ___ 分钟 |
| 大纲覆盖了几个维度 | ___/4 |
| 大纲质量（1-5） | ___（1=泛泛而谈，5=看完就想去做原型） |
| 你是否需要确认/修改大纲 | 是/否 → 如果是，改了什么？ |
| **卡住的地方** | 自由记录 |

**重点观察**：
- 大纲和"完整策划案"的区别在哪里？（如果 Claude 直接写了一份 3000 字的方案，说明阶段二和阶段三的边界确实有问题——这验证了 P1-1）
- 你作为制作人，看到大纲后的第一反应是什么？是"方向对，继续"还是"不对，得改"？

---

### 阶段三 - Step A：方案生成（目标 15-20 分钟）

**操作**：
1. 让 Claude 把大纲扩写为完整策划案初稿
2. 输出保存/覆盖到 `draft-[功能名].md`

**走查记录**：

| 记录项 | 内容 |
|--------|------|
| 实际耗时 | ___ 分钟 |
| 初稿字数 | 约 ___ 字 |
| 初稿质量（1-5） | ___（1=拼凑感强，5=像个真策划写的） |
| **卡住的地方** | 自由记录 |

**重点观察**：
- draft 文件的格式，Gemma4 脚本能直接读吗？（格式匹配是第一关）
- 初稿是否保留了大纲阶段的"核心体验目标"？还是写着写着就变成了机制罗列？

---

### 阶段三 - Step B：Gemma4 盲审 + 虚拟用户行为测试（目标 10-15 分钟）

**操作（盲审）**：
1. 把 `draft-[功能名].md` 喂给 Gemma4 审查脚本
2. 等待输出
3. 输出保存到 `review-[功能名].md`

**操作（虚拟用户行为侧测试）**——与盲审同步进行：
4. 从 3 个虚拟用户中随机选 2-3 个（每轮不固定，模拟正式流程的角色轮换）
5. 取出选中用户的 Prompt B（行为侧），把 `draft-[功能名].md` 的内容插入 prompt 中的指定位置
6. 从情境变量池中为每个用户随机抽一条，插入 Prompt B
7. 在 Gemma4（或其他独立 LLM）上逐个运行 Prompt B，记录输出
8. 汇总到 `walkthrough/[案例名]/player-behaviors-[功能名].md`

> **关键**：行为侧测试的输出（`player-behaviors-*.md`）在这次走查中**不要给 Cursor Claude 看**。模拟正式流程中 Design Agent 对行为侧输出不可见的隔离规则。

**走查记录**：

| 记录项 | 内容 |
|--------|------|
| 实际耗时 | ___ 分钟（盲审 ___min + 行为测试 ___min） |
| 脚本是否顺利执行 | 是/否 → 如果否，报了什么错？ |
| 启用了几个引擎 | ___/6 |
| 发现了几个问题 | P0: ___ 个, P1: ___ 个, P2: ___ 个 |
| 审查质量（1-5） | ___（1=全是废话，5=每条都精准戳中弱点） |
| 虚拟用户行为测试参与数 | ___/3 个用户 |
| 行为侧回答是否有洞察 | 有（举例）/ 没有 |
| 情境变量是否影响了输出 | 明显影响 / 轻微影响 / 无影响 |
| **卡住的地方** | 自由记录 |

**重点观察**：
- Gemma4 输出的 review 格式，Cursor Claude 能顺畅读取吗？（两个 Agent 之间的"通信协议"测试）
- 审查意见是否和你心里想的问题对得上？
- **虚拟用户的行为预测和审查意见是否互补？** 审查引擎找的是逻辑漏洞，虚拟用户找的是体验痛点——如果两者发现的是同一类问题，说明虚拟用户的增量价值有限
- **虚拟用户有没有发现审查引擎没发现的问题？** 这是虚拟用户体系价值的核心证据
- **情境变量有没有让同一个用户产生不同反应？** 如果换了情境但回答几乎一样 → 情境变量的设计需要加强

---

### 阶段三 - Step C：修复与捍卫（目标 10-15 分钟）

**操作**：
1. 回到 Cursor 会话，把 `review-[功能名].md` 的内容贴给 Claude
2. 告诉它："这是审查意见。修复 Fatal 问题，但不能破坏核心体验目标。如果某条意见会扼杀趣味性，提出妥协方案或设计捍卫。"
3. Claude 更新 `draft-[功能名].md`

**走查记录**：

| 记录项 | 内容 |
|--------|------|
| 实际耗时 | ___ 分钟 |
| 修复了几个 Fatal | ___/___ |
| 捍卫/妥协了几个 | ___ 个 |
| 修复后核心体验是否被保留 | 是/否 → 如果否，什么被改掉了？ |
| **卡住的地方** | 自由记录 |

**重点观察**：
- Claude 是否理解"修复但不破坏体验"这个要求？（这是 Design Agent 最难的能力）
- "设计捍卫"写得怎么样？是有理有据的反驳，还是敷衍的"我觉得没问题"？
- 你作为制作人，看完修复后的版本，核心体验还在吗？

---

### 阶段三 - Step D：第二轮审查（可选，如果时间够）

重复 Step B + Step C。观察：
- 第二轮 Gemma4 是否发现了新的 Fatal？（如果是 = 收敛条件需要调整，验证 P1-3）
- 总体质量是否在提升？

---

### 阶段四：人类终审（目标 10-15 分钟）

**操作**：
1. 你作为制作人，完整阅读最终版 `draft-[功能名].md`
2. 参考 `review-[功能名].md` 中的审查意见
3. **阅读 `player-behaviors-[功能名].md`**——这是你在本次走查中第一次看到虚拟用户的行为预测
4. 综合三份材料，给出终审意见

**走查记录**：

| 记录项 | 内容 |
|--------|------|
| 最终方案质量（1-10） | ___ |
| 与你脑中预期的差距 | 大/中/小/超预期 |
| 虚拟用户行为报告对你的终审有帮助吗 | 有（改变了你的判断/补充了你没想到的点）/ 没有 |
| 三份材料中最有价值的是哪份 | draft / review / player-behaviors |
| 你会给什么修改意见 | 自由记录 |
| 这份方案能直接交给策划去细化吗 | 能/不能 → 差什么？ |

## 三、走查结束后的复盘

走查完成后，花 15 分钟做复盘。填写下表：

### 3.1 全流程耗时

| 阶段 | 计划耗时 | 实际耗时 | 差异原因 |
|------|---------|---------|---------|
| 信息收集 + 虚拟用户需求访谈 | 15-20min | | |
| 创意大纲 | 10-15min | | |
| 方案生成 | 15-20min | | |
| Gemma4 审查 + 虚拟用户行为测试 | 10-15min | | |
| 修复/捍卫 | 10-15min | | |
| 人类终审（含行为报告阅读） | 10-15min | | |
| **合计** | **70-100min** | | |

### 3.2 断点汇总

把走查中所有"卡住的地方"汇总，按类型分类：

| # | 断点描述 | 类型 | 影响 | 建议修订 |
|---|---------|------|------|---------|
| 1 | | spec 缺口 / prompt 问题 / 工具问题 / 格式问题 | | |
| 2 | | | | |
| ... | | | | |

### 3.3 关键判断

回答以下问题（直觉回答即可）：

1. **这条链路有价值吗？** 对抗式生成出来的方案，比直接让 Claude 一次性写一份方案，质量高多少？
   - 明显更好 / 略好 / 差不多 / 反而更差

2. **瓶颈在哪？** 整条链路中，质量最差的一环是什么？
   - Design Agent 的创意能力 / Gemma4 的审查精度 / 虚拟用户的回答质量 / 两者之间的"通信"格式 / 流程本身的设计

3. **虚拟用户有增量价值吗？** 虚拟用户的参与让最终方案比"没有虚拟用户、只靠审查引擎"好多少？
   - 明显更好（发现了审查引擎没发现的问题）
   - 略好（锦上添花但不改变大方向）
   - 差不多（没什么增量）
   - 反而干扰了（噪音太多）

4. **需求侧/行为侧分离有效吗？** Design Agent 只看到需求侧、看不到行为侧，这个隔离有没有实际效果？
   - 有效（能感到 Design Agent 没有"为了过稿而设计"）
   - 不确定（需要更多轮次才能判断）
   - 无效（Design Agent 似乎不受影响）

5. **MVP 该做到什么程度？** 基于这次走查的体感：
   - 全流程自动化（四阶段 + 多轮对抗 + 虚拟用户）
   - 半自动（人触发每个阶段，Agent 执行）
   - 只做阶段一 + 阶段三的单轮审查（不含虚拟用户）
   - 只做阶段一 + 阶段三的单轮审查（含虚拟用户）

## 四、走查产出物清单

走查结束后，你的工作目录里应该有这些文件：

```
walkthrough/[案例名]/
├── draft-[功能名].md              ← 最终版策划案草稿
├── draft-[功能名]-v1.md           ← 第一轮初稿（审查前备份）
├── review-[功能名].md             ← Gemma4 审查意见
├── review-[功能名]-r2.md          ← 第二轮审查意见（如有）
├── player-desires-[功能名].md     ← 虚拟用户需求侧访谈（Design Agent 可见）
├── player-behaviors-[功能名].md   ← 虚拟用户行为侧测试（Design Agent 不可见）
└── walkthrough-log.md             ← 走查记录表（本文档的填写版）
```

这些文件本身就是 spec 修订的最佳素材——每一处卡顿都对应一个需要在 spec 里补上的细节。

## 附录：走查中虚拟用户相关的重点验证项

走查完成后，除了整体复盘，还要单独回答以下虚拟用户专项问题（这些答案直接决定正式版虚拟用户体系要不要做、怎么做）：
