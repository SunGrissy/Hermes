# Game Craft Skill Design Spec

## 1. Overview
`game-craft` 是一款基于"黑板架构（Blackboard Architecture）"与"对抗式生成思想"的 AI 辅助游戏设计方案生成工具。
它的核心目标是：**将人类的"粗略创意点子"，通过结构化的信息收集、创意推演、以及"创造者与审查者"的对抗迭代，最终转化为高质量、可交付的游戏系统/玩法策划案。**

本设计充分考虑了未来向 Web 服务及全自动 Multi-Agent 系统的演进，采用"状态外置"的文档驱动模式。

## 2. 核心架构：黑板模型与对抗式架构 (Blackboard & Adversarial Architecture)
为了保护设计的"趣味性"和"创造力"，避免"既当裁判又当运动员"导致的平庸设计，本系统将 AI 分为两个互不相识的独立角色，通过 Markdown 文件（黑板）进行异步交接：
*   **Design Agent (创造者)**：偏向正面、鼓励好体验。优化目标是"好玩、心流、爽感"。使用独立的【创意生成框架】。
*   **Review Agent (审查者)**：偏向寻找问题、识别风险。优化目标是"逻辑严密、不踩红线"。使用 `game-review` 的【6大审查引擎】。

### 2.1 执行架构（已确认）

```
Design Agent = Cursor 会话中的 Claude（创造者）
Review Agent = 本地 Gemma4 审查脚本（审查者，复用 game-review SKILL 知识库）
```

两个角色运行在不同的模型、不同的进程中，不共享上下文——天然的物理隔离，保证"盲审"的真实性。

### 2.2 核心资产 (Artifacts)
*   **输入区**：`draft-[功能名].md`（记录原始创意、核心体验目标、创意大纲、方案草稿）
*   **评审区**：`review-[功能名].md`（记录 Review Agent 的审查意见、风险点）
*   **玩家视角区**：`player-desires-[功能名].md`（需求侧访谈）/ `player-behaviors-[功能名].md`（行为侧模拟）

## 3. 工作流设计 (Workflow)

### 阶段一：信息收集与体验对齐 (Information Gathering - Design Agent)
*   **触发**：用户输入一个粗略的想法（如"做一个钓鱼小游戏"）。
*   **动作**：
    1.  Design Agent 扮演创意向导，提出 3-5 个关键问题，专注于**体验和趣味性**（如：玩家最爽的瞬间是什么？核心玩法循环是怎样的？想要传达什么情感？）。
    2.  **虚拟用户需求侧访谈**：从虚拟用户档案库中抽取 3-5 个典型用户，以"需求侧"视角提问——"你在游戏里最期待什么体验？什么时候最爽？什么时候最烦？"。输出写入 `player-desires-[功能名].md`。Design Agent 读取此文件，作为理解玩家期待的补充输入。
    3.  提取出**核心体验目标 (Core Hook/Fantasy)**。
    4.  在工作区创建 `draft-[功能名].md`，写入核心体验目标。

### 阶段二：创意大纲推演与确认 (Creative Outline & Gate - Design Agent)
*   **动作**：
    1.  Design Agent 基于核心体验目标 + 玩家需求画像，应用【创意生成框架】（核心循环、爽点释放、成长反馈、情境包装），推演出一套"创意大纲"。
    2.  大纲写入 `draft-[功能名].md`。
*   **Gate (MVP 阶段)**：系统暂停，要求人类确认大纲。人类确保大纲足够"好玩"且符合预期。

### 阶段三：方案生成与"创造-审查"对抗循环 (Generation & Adversarial Loop)
*   **动作**：
    1.  **生成初稿**：大纲确认后，Design Agent 将其扩写为完整的策划案初稿，覆盖 `draft-[功能名].md`。
    2.  **进入对抗审查循环**：
        *   **盲审 (Review Agent)**：盲审 = Review Agent 绝对不读取 Design Agent 的私有工作笔记或内心独白，只读取 `draft-[功能名].md` 的最终输出。应用 6 大引擎进行无情审查，寻找漏洞和风险。意见写入 `review-[功能名].md`。
        *   **虚拟用户行为侧测试**：同步进行——从虚拟用户档案库中随机抽取 3-4 个典型用户（每轮随机，不固定），以"行为侧"视角回答："看到这份设计方案，你周一到周五每天会怎么玩？第三天你还会上线吗？什么情况下你会放弃？"。输出写入 `player-behaviors-[功能名].md`。此文件仅供 Review Agent 和人类终审阅读，**Design Agent 不可见**。
        *   **修复与捍卫 (Design Agent)**：Design Agent 读取 `review-[功能名].md` 中的审查意见（不读取 `player-behaviors-*.md`）。它必须修复 Review Agent 提出的致命风险（Fatal），但**必须在不破坏"核心体验目标"的前提下**进行修改。如果某条修改意见会扼杀趣味性，Design Agent 需要在文档中提出"妥协方案"或"设计捍卫"。
        *   **停转条件 (Stop Condition)**：重复此过程，直到满足以下任一条件：
            1.  本轮 Review 未发现新增 Fatal（可有遗留 P1/P2），且 Design Agent 对每个 Fatal 要么已修复、要么已提出设计捍卫 + 妥协方案。
            2.  达到最大迭代轮数（3 轮）。超时则强制跳出，交由人类 Gate 裁决。

### 阶段四：人类终审与反馈迭代 (Human Final Review)
*   **动作**：
    1.  提交经过对抗打磨的最终版 `draft-[功能名].md` 给人类审查。
    2.  人类同时阅读：方案本体 + 审查意见 (`review-*.md`) + **虚拟用户行为报告** (`player-behaviors-*.md`)。
    3.  人类阅读方案及评审历史。如果提出修改意见，Design Agent 再次更新草案，并重新触发阶段三的对抗循环。
    4.  最终人类确认通过，生成可交付版本。

## 4. 框架解耦 (Framework Separation)
为了保证创造力，设计与审查的坐标系必须解耦：
*   **Design Agent 框架 (创造力导向)**：核心循环 (Core Loop)、爽点/心流 (Hook/Flow)、成长/驱动力 (Progression)、包装/情境 (Context)。
    *   *注：Design Agent 负责定义"核心体验目标（Hook）"，即"我们想提供什么爽"。*
*   **Review Agent 框架 (风险导向)**：Purpose, Rhythm, RedLine, Value, Segment, Economy。
    *   *注：Review Agent 的 Purpose 引擎负责验证"文档里写的机制逻辑上能否支撑这个目的、是否可验证"。同一事实，两套透镜，避免概念打架。*

## 5. 虚拟用户体系 (Virtual Player System)

### 5.1 设计意图

现有的 Design Agent + Review Agent 覆盖了"创造者视角"和"审查者视角"，但缺少"玩家视角"。虚拟用户体系补上这个缺口——不是靠策划猜测玩家想法，而是用数据炼化出来的典型用户画像来模拟真实玩家的反应。

### 5.2 虚拟用户的来源：数据炼化而非拍脑袋

虚拟用户档案**不靠人工编写**，而是从线上行为数据中提炼：

```
线上行为日志 → 特征提取 → 聚类分群 → 行为叙事化 → 虚拟用户 Prompt
```

**详细流程见独立文档**：[`virtual-player-creation-guide.md`](virtual-player-creation-guide.md)

核心要点：
- **用行为特征而非 KPI 指标**：LLM 理解"他每天晚上 9 点上线打 45 分钟"，不理解"他的 D7 留存是 45%"
- **聚类数量由数据决定**：不预设几个群，跑 3-10 群对比轮廓系数取最优解，最终保留 5-8 个
- **叙事化是关键转换**：把聚类中心的统计特征转写为第一人称的行为叙事，这是"数据"变成"可用 prompt"的桥梁
- **定期更新**：建议每季度用最新 3 个月数据重新聚类，避免画像与实际用户脱节

### 5.3 需求侧与行为侧分离：防止"为了过稿而设计"

同一套虚拟用户在设计和审查阶段各出场一次，但**问的问题不同，输出的文件不同，可见性不同**：

| | 需求侧（阶段一使用） | 行为侧（阶段三使用） |
|---|----------------------|---------------------|
| **问的问题** | "你在游戏里最期待什么体验？" | "看到这份方案，你这一周会怎么玩？" |
| **输出类型** | 欲望和期待（前瞻性、理想化） | 行为预测（反应性、现实的） |
| **输出文件** | `player-desires-[功能名].md` | `player-behaviors-[功能名].md` |
| **谁可以读** | Design Agent ✅ / Review Agent ✅ / 人类 ✅ | Design Agent ❌ / Review Agent ✅ / 人类 ✅ |
| **物理隔离** | Cursor Claude 会话中生成 | Gemma4 脚本中生成 |

**为什么要分离**：人想要的和人实际会做的经常矛盾。玩家说"我想要公平的 PVP"，但实际行为是花钱碾压比自己弱的人。Design Agent 只看到"想要什么"，按此设计；Review Agent 再用"实际会怎么做"来检验方案是否经得起真实行为的考验。Design Agent 无法针对行为侧输出做优化，因为它根本看不到。

### 5.4 防过拟合机制

即使做了需求侧/行为侧分离，多轮迭代后 Design Agent 仍可能通过人类终审反馈间接学到行为侧的倾向。以下机制防止这种"慢性作弊"：

| 机制 | 做法 |
|------|------|
| **角色轮换** | 每轮迭代从 5-8 个虚拟用户中随机抽 3-4 个参与行为测试，不固定名单。Design Agent 无法确定下一轮谁来 |
| **情境噪声** | 行为侧 prompt 注入随机情境变量（"这周你刚被公会踢了""你这个月已经充了 2000 块正在后悔"），同一用户在不同轮次反应不同 |
| **妥协审计** | 如果 Design Agent 连续 2 轮在同一个点上妥协，标记为"可能在拟合审查"，提交人类判断 |

## 6. 未来演进：终极形态 (The Ultimate Form)

> **注：本节为远期愿景，非 MVP 范围。**

在终极形态下，人类仅参与：
1.  **最初的创意输入**。
2.  **阶段四的最终文档审核**。
中间的"创意推演 -> 草案生成 -> 盲审 -> 修复/捍卫 -> 再次盲审"将完全由两个互相对抗的 Agent 组成的流水线自动完成，从而在"趣味"与"可交付"之间做显式的权衡（Pareto / 妥协记录），而不是追求虚无的"唯一最优解"。
