## 1. 背景与目标

### 1.1 背景

- 制作人在 **碎片化时间** 中需要向队列投递「意图 + 验收」，由 **Agent 与人类同事** 异步并行推进；回归时能 **一眼看到进度**，减少对个人记忆与口头派工的依赖。
- 已明确：**设计文档无法事无巨细**；大量增改来自使用过程，未必回填长文设计。
- 已放弃「仅用轻量替身队列模拟」的路径，改为 **直接讨论并实施 Multica 接入**。

### 1.2 目标（可验收）

1. **队列真相源**：任务以 Multica Issue 为对象，具备指派、状态、评论时间线。
2. **人机同板**：人类与 Agent（含多 Runtime）在同一工作空间内认领与更新。
3. **记录链完整**：**Multica（已关闭/已验收）+ WORK_LOG** 构成完整工作记录；**设计文档 + Multica 演进** 构成完整设计意图与变更史（文档为地图与原则，工单为航行日志）。
4. **与现有仓库纪律兼容**：不改变根仓库对子模块、`acceptance-checklist`、敏感数据的基本约定；Multica 侧不存放密钥明文。

### 1.3 非目标（首版不做）

- 用 Multica **替代** PM 系统内业务数据（版本/Feature 等仍留在 pm-system）。
- 在首阶段把 **全部** 历史 WORK_LOG 迁入 Multica。
- 替制作人自动做 **优先级与架构取舍**（仍由人担任队列 Owner）。

## 2. 需求摘要

| 类型 | 需求 |
|------|------|
| 功能 | 工作空间隔离；Issue 创建/指派/状态；Agent daemon 对接；可选与 GitHub 仓库关联（若 Multica 支持该工作流）；**钉钉派单/通知适配服务**（见 §5–§6） |
| 流程 | 碎片时间：**钉钉或 Multica 开/评 Issue**；关单：**摘要 + 指向 WORK_LOG 条目**；WORK_LOG：**一句反向链接 Issue** |
| 文档 | 长文设计 **按需** 合并；**不**要求每次小改同步 `producer-tower-design.md` |
| 安全 | 内网/数据驻留策略与 LLM 调用边界在部署方案中必选其一 |
| 运维 | 谁负责升级、备份、账号；失败时降级策略（仍用 Cursor 会话） |

## 3. 方案对比（三选一 + 推荐）

### 方案 A：Multica Cloud + 本机 / 内网 Daemon

- **优点**：上线最快；官方托管升级。
- **缺点**：任务描述与评论可能出内网；合规需自行评估。
- **适用**：先试跑流程、无强数据驻留要求。

### 方案 B：全栈自托管（Docker，内网）

- **优点**：数据与元数据可控；与现有「内网 PM / TR」心智一致。
- **缺点**：运维与升级成本；需机器与 Postgres。
- **适用**：已确定工单内容不得上公网。

### 方案 C：混合

- **板子与协作**：Cloud 或自托管二选一；**敏感细节**仅在 Issue 写「见内网 WORK_LOG / 见某 commit」，正文脱敏。
- **缺点**：双写纪律要求高。
- **适用**：想快启又要控敏。

**推荐**：若 **无强制内网**：先 **A** 跑通 2～4 周流程，再决定是否迁 **B**。若 **强制内网**：直接 **B**，不做 A 试水。

### 3.1 当前拍板（2026-04-18）

- **部署**：现阶段采用 **方案 A（Multica Cloud + 本机 / 内网 Daemon）**；**全链路跑通并复盘后**再评估是否有必要切换到 **方案 B**（与上节推荐一致）。  
- **合规**：若试点 Issue 中出现不宜出内网的描述，须执行 **脱敏** 或临时改走 §3 方案 C 的写法，直至迁 B。

## 4. 推荐架构（逻辑层）

```
制作人 / TL ──► Multica Issue（意图、DoD、指派、评论）
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   Agent Runtime  同事    （可选）PR / 本地分支
        │           │
        └───────────┴──► 合并后 WORK_LOG + 关单摘要
```

- **MyAgents 仓库**：仍为主体代码与 `.cursor/skills`；Multica **不替代** Skill 与门禁文本。
- **设计文档**：里程碑或对外说明时，从已关闭 Issue **抽取**一节合并进 `docs/` 或模块设计 md。

## 5. 钉钉与 Multica：接入后的端到端工作流

前提：已有 **完全自控的钉钉企业自建机器人**，支持 **私聊** 与 **群内 @ 机器人** 接收消息（钉钉开放平台事件订阅 + HTTP 回调或 Stream；验签与解密仅在自建服务侧完成）。

```
私聊 / 群内 @ 机器人发送派单文案
              │
              ▼
钉钉开放平台 ──HTTP──► 「派单适配服务」（自建）
              │              │
              │              ├── 鉴权、解析（可用固定格式，如 #派单 + 标题/一行说明，降低误触）
              │              └── 调用 Multica API → 创建或更新 Issue（指派、标签、DoD）
              │
              ▼
Multica：人类伙伴与各 Agent 在站内看到任务；认领、改状态、评论、在 Runtime 上执行
              │
              ▼
关单 / 验收：Issue 内保留摘要；与 PR、WORK_LOG 互链（纪律见 §7）
              │
              ▼
（可选）Multica 事件出站 → 自建服务 → 钉钉机器人 → 通知制作人 / 群（见 §6）
```

**流程语义**（与讨论结论一致）：

1. **派单**：通过 **钉钉对话**（私聊或群 @）触发 → 适配层写入 **Multica**。  
2. **执行**：制作人或伙伴的 **Agent**、或 **人类**，在 Multica 上 **认领并处理**。  
3. **记录**：以 **Multica Issue 状态与评论** 为主；关单与 **WORK_LOG** 对齐、互链。  
4. **触达**：若要求 **「伙伴 / 制作人必须在钉钉收到强提醒」**，依赖 **§6 自建出站**，不能默认 Multica 已对接钉钉。

## 6. 能力边界：Multica 自带 vs 需自建钉钉衔接

| 环节 | Multica 侧（产品内建或默认提供） | 钉钉侧（须我们自建） |
|------|-----------------------------------|----------------------|
| Issue 创建、指派、状态、标签、评论时间线 | ✅ | **入站**：机器人收消息 → 适配服务调 Multica **REST/API**（非 Multica 内置钉钉） |
| Agent / 人类认领、多 Runtime、站内执行与进度 | ✅ | — |
| 指派后的 **站内 / 邮件** 等通知（以产品实际为准） | ✅ 依开通项 | **不等于**钉钉工作通知；若要钉钉响铃 → 自建 |
| 新建单、改状态、关单时 **自动推送到指定人钉钉** | ⚠️ **勿默认支持** | ✅ 适配层或 **Multica Webhook（若可用）** → 调钉钉 **工作通知 / 群机器人** |
| 私聊 / 群 @ **派单入站** | — | ✅ 已有企业机器人时，由回调服务衔接 Multica |

**结论**：

- **业务真相与执行枢纽**在 **Multica**（Issue + 认领 + Agent）。  
- **钉钉是习惯触达面**：**入站派单**、**出站通知** 两条链路，在默认产品形态下均需 **自建「钉钉 ↔ Multica」适配**；Multica 不承担「替你接好钉钉」的保证。

## 7. 工作习惯（接入后固定纪律）

1. **碎片时间**：优先 **Issue 标题 + DoD 一行**；长文后补。
2. **关单**：评论固定含 **「交付摘要 + WORK_LOG 日期标题」**；必要时 **「建议同步文档的章节号」**（可选）。
3. **WORK_LOG**：每条交付 **末尾加 `Multica: #编号` 或链接**（若平台 URL 固定）。
4. **小改不回填设计文档**：默认允许；**中/大改**再开文档子任务或单独 Issue「合并设计说明」。

## 8. 首阶段试点（建议）

- **试点主战场**：**以 `pm-system` 为主**——Issue 描述、分支与 PR 默认指向 `pm-system/`；根仓库其它子项目、大范围子模块指针变更 **不作为首 4 周必达项**，若出现须 **单独开 Issue** 说明范围。  
- **试点仓库/空间**：单一 Multica **Workspace**，命名与 **pm-system**（或 MyAgents 内 pm-system 条线）对齐，避免多板子漂移。  
- **试点工单类型**（3 类以内）：  
  - `feat` / `fix`：**优先** pm-system 内明确小功能；  
  - `chore`：文档与 Skill 小补（若进板子）；  
  - `spike`：调研类（如「自托管资源清单」），限时关单。  
- **成功标准（4 周内）**：≥10 条真实 Issue 走完认领→PR/说明→关单→`pm-system/WORK_LOG.md`（或约定路径）；至少 1 条由非你本人认领；无 P0 泄露事件。
