# Design Council / Game Review 类 Skill 优化提醒

> **用途**：之后继续迭代 `boss-design-council`、`game-design-council`、`game-review` 时，用来对齐思路、固定标准、避免「改爽了但退化」。  
> **方法来源**：借鉴 [darwin-skill](https://github.com/alchaincyf/darwin-skill) 的「评估 → 改进 → 实测 → 保留或回滚」与棘轮思想；落地形态由本仓库自行裁剪，**不要求**安装任何外部 CLI。

---

## 1. 先对齐三份 Skill 的分工（改之前读一遍）

| Skill | 路径 | 它是什么 | 它不是什么 |
|-------|------|----------|------------|
| Boss 设计智囊团 | `.cursor/skills/boss-design-council/SKILL.md` | Boss **加分表演**、认知科学向 **多视角对话自检** | 纯数值平衡、纯美术风格终审 |
| 游戏设计智囊团 | `.cursor/skills/game-design-council/SKILL.md` | 玩法/系统/经济/社交草案的 **智囊团对话自检** | `game-review` 的替代品；纯数值调参 |
| 策划方案审核 | `.cursor/skills/game-review/SKILL.md` | **6 大引擎**逻辑完整性 + Gate/Flag/Sense **双层协作** | 单靠 AI 下最终审美结论 |

**迭代纪律**：改其中一个时，在 PR/自测里显式回答——是否**越界抢了**另外两个的职责、或是否与 `partner-router` / 命令触发说明冲突。

---

## 2. 优化的北极星（比「写得更长」重要）

1. **可执行**：Agent 打开 Skill 后，下一步动作清晰（先问什么、输出什么结构、何时停）。  
2. **可回归**：同一批「黄金输入」下，**结构块不少、禁项不踩**；变差能指认是哪次改动。  
3. **可分辨**：智囊团输出仍是「**提问与对话引导**」气质；`game-review` 仍是「**引擎串行 + 决策问题**」气质，勿混成一种模板。  
4. **人审不可替代**：品味、红线取舍、制作人 sense **不**交给「自动总分」替你做决定。

---

## 3. 推荐工作流（达尔文式，适配本仓库）

### 3.1 一次只动一个主资产

- **默认**：单次迭代只改 **一个** `SKILL.md`（或明确列出的一组 `references/*.md` 从属于同一次实验）。  
- **禁止**：同一轮里又改智囊团文案、又大改 `game-review` 引擎引用，最后无法归因。

### 3.2 先写「考卷」再改「教材」

为每个 Skill 维护一小份 **黄金用例**（可先放在本文件同目录下的 `design-council-review-golden-prompts.md`，或各 Skill 目录内的 `tests/golden-prompts.md`，按你后续习惯定稿即可）：

| 用例类型 | 目的 |
|----------|------|
| 典型稿 | 基线：结构完整、语气正确 |
| 边界稿 | 信息极少 / 极多、半截方案 |
| 烂稿 | 故意踩红灯，看是否还能守住引导方式 |
| 错域稿 | 应触发 **When NOT to use** 或礼貌 redirect |

每个用例至少注明：**输入摘要**、**期望输出必须包含的块**（见下一节）、**禁止出现的模式**（例如智囊团变成逐条检查表、review 漏引擎）。

### 3.3 最低合格输出 schema（迭代时用来判 PASS/FAIL）

**智囊团（Boss / Game 共用逻辑，各自列表不同）**

- 开场短：说明角色与目的（对话自检，非终审）。  
- **六位**（或文档约定的席位数）均有独立段落或小节标题。  
- 每位至少：**关注维度 + 1～2 个可回答的提问**；若有「红灯判断」则与正文一致、勿空洞。  
- 收尾：汇总「下一步建议策划自己回答什么」或等价行动引导。

**game-review**

- 引擎选择与裁剪说明（或内嵌在流程里但**可被读者看到**）。  
- 已启用引擎的**结论/风险**与 **Gate/Flag/Sense 决策问题**分离清晰。  
- 若文档声明了 `/game.review` 等命令行为，示例或步骤须与之一致。

以上 schema 用 **人工 + 可选脚本** 检查即可，不必一开始就做自动打分。

### 3.4 小步提交 + 棘轮心态

- 每轮改动：**小 commit**，消息写清「为哪条用例/哪个维度服务」。  
- 若发现某次改动让黄金用例变差：**优先回滚该 commit**，再从上一好基线重试，而不是在同一 diff 上叠补丁叠到看不清。  
- 「分数」若用：只作**自建核对表**的勾选统计即可；**不要**让分数替代你对「像不像智囊团 / 是否削弱人审」的判断。

### 3.5 子视角 / 独立审阅（防自嗨）

- 改完 Skill 后，理想情况用**另一会话**或「只喂 Skill + 用例、不喂你的解释」让模型跑一遍，看是否**照本宣科仍稳定**。  
- 若你本人就是唯一审阅者：至少隔**几小时或隔天**再看一遍 diff，减少当下盲点。

## 4. 评估维度建议（简版 rubric）

可按需打勾（不必量化到 100 分）：

**A. 结构（硬）**

- [ ] Frontmatter `name` / `description` 与 `partner-router`、实际触发场景一致。  
- [ ] When to use / When NOT to use 边界清楚且与另两个 Skill 无逻辑打架。  
- [ ] 章节顺序符合阅读路径：概述 → 何时用 → 流程/席次 → 细节 → 附录。

**B. 行为（半硬）**

- [ ] 黄金用例全部 PASS；至少一条「错域」用例被正确拒绝或 redirect。  
- [ ] 未引入与 `cognitive-design-engine` 等冲突的「伪科学断言」；引用保留可追溯。

**C. 气质（软，但必须人审）**

- [ ] 智囊团仍是「**问与思**」，未退化成只有 checklist。  
- [ ] `game-review` 仍明确 **AI 逻辑层 / 人直觉层** 分工，未暗示 AI 可单独拍板。

---

## 5. 反模式清单（踩了就该停手想清楚）

1. **为涨分缩智**：删减深度、把提问改成陈述，短期「更好执行」，长期毁掉智囊团价值。  
2. **测试集过窄**：两三份自家方案来回拟合，上线后对新品类完全不对。  
3. **把 council 写成 mini game-review**：六引擎化、报告体，会混淆路由与预期。  
4. **大改 references 却不跑黄金用例**：`game-review` 的 `references/engine-*.md` 一动，全文连锁。  
5. **一次合并多个主题**（Boss 信号链 + 通用循环 + 经济通胀）— 归因失败，回滚成本极高。

---

## 6. 合并前自检（可复制）

```
[ ] 本轮只改一个主 Skill（或已声明的一组从属文件）
[ ] 黄金用例已更新 / 已重跑（列出用例文件名）
[ ] 与另两个 Skill 的边界已复核
[ ] partner-router / 命令文档无需同步 或 已同步
[ ] 大段心智/科学表述已人审（非仅格式）
[ ] 若失败可回滚：commit 粒度 OK
```

## 7. 与仓库既有规范的关系

- Skill 生命周期与「提议—人确认—再落地」的总原则见：`.cursor/rules/skill-evolution.mdc`。  
- 本提醒文档不替代该规范；冲突时以 **skill-evolution + 制作人边界** 为准。

## 8. 可选下一步（非必须）

若迭代频率变高，再考虑：

- 为三个 Skill 各建 `golden-prompts` 文件 + 最小 JSON/Markdown 报告 schema（便于以后半自动对比）。  
- 在 `WORK_LOG.md` 或某次会话结论里记一笔：**本轮改了哪条原则、为哪类方案服务**，方便半年后还记得为什么这样写。

---

**一句话**：把三个 Skill 当「**要带 CI 的产品**」——**考卷固定、小步、可回滚、结构用勾选守住、品味用人守住**。
