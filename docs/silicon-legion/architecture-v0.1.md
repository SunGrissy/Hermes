## 一、核心设计决策（已确认）

### 1.1 三层架构模型

```
┌─────────────────────────────────────────┐
│  Layer 3: 主权层（Sovereign）            │
│  用户（孙懿）——最终拍板与资源调配          │
└─────────────────────────────────────────┘
                    ▲
                    │ 总管汇总建议 + 用户补充/判断
┌─────────────────────────────────────────┐
│  Layer 2: 总管层（Director）             │
│  小橘（Hermes）——认知汇聚、冲突消解、      │
│  形成今日目标、拆解可执行任务              │
│  冲突裁决策略：方案C（假设性方案提案）      │
└─────────────────────────────────────────┘
                    ▲
    ┌───────────────┼───────────────┐
    ▲               ▲               ▲
┌────────┐    ┌────────┐    ┌────────┐
│ Advisor│    │ Advisor│    │ Advisor│
│  项目   │    │  人力  │    │  ...   │
│ (阿茶)  │    │ (待定) │    │        │
└────────┘    └────────┘    └────────┘
```

**关键原则**：
- 总管不替用户做**价值判断**，只做**信息整合与冲突消解**
- 当Advisor建议矛盾时，总管输出假设性方案（如"如果做A，则B需推迟到明天，是否接受？"），降低用户认知负担

### 1.2 军团成员与职责（已确认部分）

| 身份 | 名称 | 职责范围 | 状态 |
|------|------|---------|------|
| **总管** | 小橘（Hermes） | 汇聚各Advisor建议、冲突消解、形成今日工作目标、拆解执行任务 | **现有升级** |
| **PM Advisor** | 阿茶 | 项目管理视角：版本进度、里程碑风险、阻塞事项、今日应推进的项目事务 | **机器人已有，Agent待配** |
| **主策划 Advisor** | 待定 | 策划工作安排与验收视角：当前在研玩法/系统的策划进度、待验收文档、策划资源瓶颈 | **待创建** |
| **数据分析师** | 待定 | 数据视角：关键指标波动、异常数据提醒、需要用数据回答的问题 | **待创建** |
| **人力 Advisor** | 待定 | 人力/绩效视角：待完成的评价、面试安排、团队状态提醒 | **待准备** |
| **外部 Advisor** | 待定 | 外部情报视角：竞品动态、行业信息、技术更新 | **待准备** |

### 1.3 交互形式（已确认）

**群聊式建议流程**：

1. 触发条件（每日定时 / 用户主动召唤）
2. 各Advisor在**工作群**内依次/并行发言，展示各自视角的「今日建议」
3. 用户在群内看到建议后，可补充信息（如"今天有外部会议，下午不可用"）或给出判断（如"封版优先，面谈延后"）
4. 总管读取群内所有建议 + 用户反馈，输出**今日工作目标**
5. 用户确认或调整目标后，总管拆解为具体任务并跟进

**关键约束**：群里的"对话"本质上是**给用户看的汇报**，Advisor之间不需要真正"讨论"，它们各自独立输出建议，由总管做整合。

### 1.4 记忆层（已确认）

- **统一记忆层**：`D:/MyAgents/shared-memory/hub/`
- 各Advisor在生成建议前，先向hub写入其视角的关键数据（如PM Advisor写入版本阻塞点、主策划Advisor写入待验收清单）
- 总管读取hub中所有Advisor的写入内容，作为汇总输入
- 记忆汇聚机制：MemOS每日2:00自动同步，Agent身份标记清晰

## 二、MVP 架构方案（已落地）

### 2.1 代码组织

```
silicon-legion/
├─── core/                      # 共享基础设施（配置、钉钉客户端、PmSystem客户端、定时器）
│    ├─── config.py             # 支持多租户（总管/阿茶/其他Advisor各自配置）
│    ├─── dingtalk_client.py    # 钉钉API封装（token、发消息、读群历史）
│    ├─── pm_client.py          # PmSystem数据读取
│    └─── scheduler.py          # APScheduler定时任务
├─── director/                  # 总管小橘（端口8299）
│    ├─── main.py               # FastAPI入口，健康检查、汇总调度
│    └─── start.bat             # 启动脚本
└─── advisors/
     └─── pm/                    # PM阿茶（端口8300）
          ├─── main.py           # FastAPI入口 + 钉钉HTTP回调端点
          └─── start.bat       # 启动脚本
```

### 2.2 交互流程

**定时触发（9:00）**：
1. 阿茶自己的定时器触发
2. 读取PmSystem数据 → 生成建议 → 用阿茶身份发到群里
3. 小橘（可选）后续汇总其他Advisor建议

**主动召唤**：
- @小橘 → 小橘的回调端点收到消息 → 调用各Advisor或直接回复
- @阿茶 → 阿茶的回调端点收到消息 → 生成PM视角建议 → 用阿茶身份回复

### 2.3 认证与消息通道

| 成员 | 通道 | 认证方式 | 群里显示身份 |
|------|------|---------|------------|
| 小橘 | HTTP回调 + HTTP发消息 | 总管自己的钉钉应用凭证 | 小橘 |
| 阿茶 | HTTP回调 + HTTP发消息 | 阿茶的钉钉应用凭证（已有） | 阿茶 |

### 2.4 数据源

- **统一记忆层**：`shared-memory/hub/` 作为未来扩展，MVP暂不强制要求各Advisor写入
- **PmSystem接入**：各Agent独立使用 `X-Api-Key`认证，只读不写入
- **群消息读取**：各自通过钉钉HTTP回调接收，不拉取群历史

## 三、后续可做的优化和迭代方向

### 3.1 短期（MVP验证后1-2周）

| 优化点 | 说明 | 价值 |
|--------|------|------|
| **阿茶大脑LLM化** | 模板建议替换为LLM生成，输入PmSystem数据+角色Prompt | 建议质量大幅提升 |
| **群历史上下文** | 总管读取群历史消息，理解对话上下文 | 汇总更精准，假设性方案更贴切 |
| **定时触发编排** | 多Advisor串行发言，间隔1分钟，避免信息轰炸 | 用户体验优化 |
| **统一记忆层落地** | 各Advisor生成建议后写入hub，总管读hub汇总 | 解耦数据依赖，支持异步处理 |

### 3.2 中期（1-2个月）

| 优化点 | 说明 | 价值 |
|--------|------|------|
| **新Advisor接入** | 主策划Advisor、数据分析师、人力Advisor等 | 完善决策支撑网络 |
| **总管冲突消解** | 多Advisor建议矛盾时，总管生成假设性方案 | 减少用户认知负担 |
| **总管任务分派** | 总管形成目标后，识别代码任务并调度OpenClaw/Claude Code/Kimi Code | 自动化执行层 |
| **PmSystem L2聚合接口** | 专用于Advisor的聚合查询API（周汇总、风险信号等） | 数据获取效率提升 |
| **Stream模式升级** | HTTP回调替换为钉钉Stream长连接，真正实时 | 降低延迟，提升体验 |

### 3.3 长期（3个月+）

| 优化点 | 说明 | 价值 |
|--------|------|------|
| **多Agent平台化** | 从硬编码服务进化为Agent平台，支持动态添加/移除Advisor | 运营效率大幅提升 |
| **自动化管线** | 甘特/进度表 → 管线同步 → 风险预警 → 任务派发 | 少人工干预的智能管理 |
| **记忆中心升级** | 从文件系统升级为数据库/向量存储，支持高级棋筜查询 | 大规模应用基础 |
| **多模型调度** | 不同Advisor使用不同LLM（如主策划用强推理模型、数据分析用轻量模型） | 成本与效果平衡 |

- 总管（小橘）升级为认知汇聚中心

### 议题2：群聊对话机制

**已确认的实施参数**：
- 触发方式：每日9:00定时 + 用户主动召唤（@Advisor名称或@总管）
- 消息节奏：串行发送，每条间隔1分钟，给用户留出消化时间
- 上下文读取：总管需读取群历史消息来理解用户反馈和之前的对话上下文
- **群消息读取方案**：采用钉钉官方API（用户为管理员，权限可解决）

**待讨论的技术细节**：

- **消息编排与身份区分**：同一机器人账号如何在消息中展示不同Advisor身份？

## 四、实施方案对比（B vs C）

| 维度 | 方案B：常驻服务 | 方案C：混合（Cron+服务） | 差异点 |
|------|-------------|------------------|--------|
| **定时触发** | 内部scheduler（APScheduler/croniter） | 系统Cron负责定时，服务只处理HTTP召唤 | C更符合Unix习惯，但需要两套机制 |
| **主动召唤** | 服务监听HTTP端口，直接响应 | 服务监听HTTP端口，Cron不走HTTP | 一致 |
| **资源占用** | 一个Python进程常驻 | 同B | 一致 |
| **异常复原** | 进程崩溃则定时触发失败，需supervisor | Cron无进程，服务崩了只影响召唤 | C更健壮 |
| **日志/调试** | 单一日志流 | Cron日志+服务日志分离 | B更简洁 |
| **实施复杂度** | 中 | 高 | B更快 |

**推荐**：采用**方案B（常驻服务）**。理由：
1. 你的场景是"定时 + 召唤"混合，常驻服务能统一处理两种触发
2. 本地环境下一个Python进程资源成本极低
3. 可用supervisor或Windows服务管理，崩溃自动重启不是问题

## 五、PmSystem 数据源评估

**基于当前权限开发 worktree 的现状**（文档：`pm-system/docs/superpowers/specs/2026-04-22-pm-system-permissions-automation-llm-design.md`）：

### 5.1 权限架构设计
- **三轨主体**：HumanUser / ServiceJob / LLMWorker
- **API分层**：L0主数据写 / L1管线推进写 / L2聚合只读 / L3派生物写
- **实施阶段**：Phase 0清单 → Phase 1人类角色 → Phase 2 ServiceScope → Phase 3 LLM策略

### 5.2 当前已有的只读/聚合接口（适合Advisor消费）

| 接口 | 路径 | 适用对象 | 说明 |
|------|------|---------|------|
| `GET /api/data` | main.py | 总管/PM Advisor | 整包数据，含版本、Feature、任务等 |
| `GET /api/data/meta` | main.py | PM Advisor | 数据元信息 |
| `GET /api/pm-calendar` | main.py | 所有Advisor | 工作日/假日数据 |
| `GET /api/health` | main.py | 运维 | 健康检查 |
| `GET /api/version` | main.py | 运维 | 版本号 |
| `GET /api/backups` | main.py | 运维 | 备份列表 |
| 各模块 GET | routers/*.py | 分类Advisor | 版本、任务、里程碑等分类查询 |

### 5.3 对MVP的影响
- **好消息**：PmSystem已有丰富的GET接口，PM Advisor可直接消费
- **需注意**：当前权限开发中，部分原本无鉴权的写接口正在收口，建议MVP仅读取数据，不写入
- **接入方式**：可用`X-Api-Key`或JWT认证，建议为PM Advisor申请一个`ServiceJob` scoped key（`read:versions`、`read:features`、`read:planner-items`等）

### 5.4 待建设的聚合接口（L2层）
根据Spec，未来需要为Advisor提供：
- 周汇总（风险信号输入）
- 版本进度聚合视图
- 策划周计划汇总

**建议**：MVP期间先用现有GET接口组装，权限落地后再建设专用聚合接口。
