# 阿茶 · PM 工作增强方案（讨论稿）

> 状态： brainstorm 落盘，待逐项讨论
> 日期：2026-04-25
> 背景：老大（制作人兼主策划）提出 PM 工作自动化需求，阿茶从 PmSystem 取数辅助决策

---

## 一、核心定位

阿茶不是替代 PM，是**主策划的 PM 副官**。

- 主策划视角优先：保交付、打提前量、盯异常
- 数据驱动 + 毒舌播报：坏消息照报，但让人笑着接受
- 机制替代催办：能自动扫的自动扫，必须人拍的留给你

## 二、决策优先级五层（老大框架）

### 第 1 层：需要我出面的紧急情况

> 上游是否阻塞下游？我不出手就翻车？

| 信息源 | PmSystem 字段 | 阿茶能自动扫？ | 输出形态 |
|--------|--------------|---------------|---------|
| Feature 阻塞卡死下游 | `Feature.is_blocked` + `blocked_reason` | 是 | 红色警报 |
| 管线节点超期导致后续无法启动 | `Version.pipeline_status` + `pipeline_ddls` 逾期 | 是 | 红色警报 |
| 插单未决策导致版本范围悬置 | `Feature.is_rush=true` + `rush_decision` 为空 | 是 | 红色警报 |
| 制作人 checklist 未勾 | `Version.node_manual_checks` | 是 | 红色警报 |
| DoR 不足就进了开发 | `Feature.readiness` + `pipeline_status.dev=true` | 是 | 红色警报 |
| 临时人事变动导致实际无人 | 无 | **否** | 需老大输入或日报侧面提取 |
| 外部依赖口头承诺未兑现 | 无 | **否** | 需老大输入关键外部依赖 |
| 团队内部冲突 | 无 | **否** | 不扫，不在数据层 |

**阿茶输出（样例）**：
> "V2.3 的 Go/No-Go 决策已超期 2 天，阻塞冻结确认。关联 Feature'公会战'标记 rush 但无决策记录。建议：今日内拍板是否进 V2.3，否则 DDL 铁延期。"

**待讨论**：
- [ ] 红色警报阈值：管线节点逾期几天触发？插单 pending 几天触发？
- [ ] 外部依赖清单：是否维护一份"关键外部依赖"让阿茶跟踪？

---

### 第 2 层：能否给下游争取更多时间？

> 版本规划提前量够不够？what 设计和确认够不够及时？

| 信息源 | PmSystem 字段 | 阿茶能自动扫？ | 含义 |
|--------|--------------|---------------|------|
| 规划节点前推窗口 | `Version.pipeline_ddls.planning` | 是 | 是否已启动战略对齐 |
| what 层等待时长 | `Feature.design_landing.numeric.what_aligned_at` | 是 | 数值轨 WHAT 对齐了多久 |
| how 层等待时长 | `Feature.design_landing.numeric.how_aligned_at` | 是 | 方案定了多久没进 build |
| 设计到落地整体周期 | `design_landing` 各阶段时间戳 | 是 | what→make 平均多久 |
| 版本间 DDL 冲突 | 多版本 `pipeline_ddls` 重叠 | 是 | 是否同时需要同一批下游资源 |
| 基线数据 | 需 2~4 周历史积累 | **待建立** | 同类版本/Feature 平均耗时 |

**核心判断**：反事实——"如果 what 层早 3 天对齐，开发能多 3 天缓冲"

**阿茶输出（样例）**：
> "V2.4 规划节点剩余 5 个工作日，但 3 个核心 Feature 仍在 what_pending。历史同类版本 what→how 平均 4 天，意味着开发节点至少损失 3 天缓冲。建议：压缩 scoping DDL，或砍 1 个非核心 Feature 保 what 质量。"

**待讨论**：
- [ ] 基线建立：前几周数据不足，是否允许阿茶先记录、后判断？
- [ ] 版本间 DDL 冲突的"下游资源"是否包含 QA/美术/程序？这些人力在系统里吗？

### 第 3 层：有没有不应该发生的拖延？

> 这个拖延是意外，还是规律？

| 拖延类型 | 数据信号 | 自动可扫？ | 需要基线？ |
|---------|---------|-----------|-----------|
| 策划周计划条目逾期 | `WorkItem.target_week` 过期但 `status=active` | 是 | 否 |
| Feature 长期未更新 | `updated_at` 超 7 天且 `status!=done` | 是 | 否 |
| 设计到落地单轨停滞 | `design_landing` stage=pending 超阈值 | 是 | 是 |
| 版本节点反复回退 | `pipeline_status` 从 true 变 false | **需历史追踪** | 是 |
| 同一人多条连续逾期 | 按 `WorkItem.assignee` 聚合逾期率 | 是 | 是 |

**阿茶输出（样例）**：
> "李四本周 3 条 WorkItem 全部逾期。历史基线：李四平均逾期率 15%，本周 100%。模式识别：3 条均为慢轨 P0，且都是验收类（无设计产出）。建议：检查是否把设计和验收堆给同一人。"

**待讨论**：
- [ ] 基线窗口：取近 4 周还是近 8 周？是否排除节假日？
- [ ] 逾期阈值：WorkItem 超过 target_week 几天算"逾期"？
- [ ] 节点回退追踪：当前 PmSystem 不存历史状态，是否需要增加 audit log？

### 第 4 层：交付异常的原因是什么？

> 忙不过来 / 过于纠结 / 排期本身不合理？

| 原因 | 数据侧面 | 可信度 | 人工确认点 |
|------|---------|--------|-----------|
| 忙不过来 | WorkItem 数 > 均值 2x；Feature estimate 总和 > 历史周产能 | 中 | 是否有临时任务未录入 |
| 过于纠结 | design_landing 某 stage 反复 aligned/回退；review 轮次 > 均值 | 中 | 是真的在打磨还是绕圈子？ |
| 排期不合理 | WorkItem target_week 与 Feature estimate 不匹配 | 高 | 当时为什么这样排？ |
| 阻塞在第三方 | `is_blocked=true` + blocked_reason 含"等待XX" | 高 | 第三方承诺了没？ |
| 需求蔓延 | pipeline_weight=fast 但 design_landing 耗时与 slow 相当 | 中 | 是否该升格为 slow？ |

**阿茶输出（样例）**：
> "张三'公会战系统'逾期 5 天。数据侧面：① effective_points=45（均值 20），排期仅给 1 周 → 排期不合理 ② how 阶段停留 8 天（均值 3 天），无 review 记录 → 可能过度纠结或阻塞未报 ③ 本周另有 2 个 P0 → 忙不过来叠加。建议优先级：先拆排期，再解阻塞。"

**待讨论**：
- [ ] "过于纠结"的主观判断边界：阿茶只报数据侧面，不直接下"他在绕圈子"的结论？
- [ ] 排期不合理的历史基线： Feature estimate 是谁估的？策划自估还是 PM 统估？历史准度如何？

---

### 第 5 层：有没有不必要的需求蔓延？

> 快轨变慢轨、投入产出失衡

| 信号 | 数据源 | 判断逻辑 |
|------|--------|---------|
| 快轨标签 but 慢轨行为 | `pipeline_weight=fast` vs `design_landing` 轮次/耗时 | fast 档 what→make 应 ≤ X 天 |
| 内容层级与投入不匹配 | `content_tier=S` but `estimate` 很大 | S 档不应消耗 A 档工时 |
| Review 轮次过多 | `DesignReviewRound` 按 pool_item 统计 | 超阈值标记"反复打磨" |
| 范围膨胀 | 周新增 WorkItem > 完成条目，且 DDL 不动 | 版本范围在膨胀 |

**阿茶输出（样例）**：
> "Feature'新手引导调优'标记 fast 档，但 design_landing 已走 3 轮 review（fast 档均值 1 轮），耗时 12 天（均值 5 天）。建议：确认是否应升格为 slow，或砍 non-core 分支保主线。"

**待讨论**：
- [ ] fast/slow 时间阈值：fast 档 what→make 几天算正常？你定还是我看历史数据自动算？
- [ ] content_tier 与 estimate 的映射关系：是否有内部约定？

## 三、负荷均衡四维（老大框架）

### 维度 1：版本内快轨/慢轨比例

> 比较复杂，版本规划评估单独开题

**当前数据**：`pipeline_weight`（fast/slow）、`content_tier`（S/A/B/C）、`design_landing` 双轨。

**阿茶暂不深入**，待开题讨论。

**待讨论（单独开题）**：
- [ ] 版本总容量模型：一个版本能容纳多少 fast/slow？
- [ ] 内容配比规则：商业化内容 vs 系统内容 vs 体验内容的理想比例？
- [ ] 双轨并行度：数值轨和 UX 轨的产能是否独立计算？

---

### 维度 2：多版本并行节点冲突

> 比如都在测试期肯定要抢 QA

**PmSystem 能扫的**：
```
活跃版本 × 管线阶段矩阵
→ 统计同时处于 dev/acceptance/releaseTesting 的版本数
```

**阿茶输出（样例）**：
> "冲突预警：本周 V2.3 和 V2.4 同时处于 acceptance，且 V2.2 在 releaseTesting。历史模式：同时 ≥2 版本在测试期 → QA 资源紧张概率 80%。建议：确认 QA 覆盖，或错开 acceptance DDL。"

**待讨论**：
- [ ] QA/美术/程序人力是否在 PmSystem？如果不在，阿茶只能报"节点冲突"，不能报"资源够不够"。
- [ ] 冲突阈值：同时几个版本在 acceptance 算"需要关注"？

---

### 维度 3：同一时期策划交付内容的性质和量是否均衡

> 不能所有人都挂慢轨 P0 + 交付节点很近

**阿茶判断维度**（按 `WorkItem.assignee` + `target_week` 聚合）：

| 指标 | 阈值建议 | 自动标红？ |
|------|---------|-----------|
| 单人 P0 > 1 个/周 | 1 | 是 |
| 单人 slow 档占比 > 50% | 50% | 是 |
| 交付节点 ≤ 3 天且 P0 > 0 | 3 天 | 是 |
| 所有策划 P0 集中在同一版本 | — | 黄（风险提示） |

**阿茶输出（样例）**：
> "负荷失衡：本周 4 个策划各挂 1 个 slow P0，交付节点均在 3 天内。模式：'所有人冲刺同一版本'。下游冲击：开发阶段将同时涌入 4 个核心 Feature。建议：① 错开交付节点 ② 或降级 2 个 P0 为 P1。"

**待讨论**：
- [ ] 阈值确认：上述阈值是否符合团队实际？
- [ ] "慢轨"定义：仅看 `pipeline_weight=slow`，还是也看 `design_landing` 实际耗时？

---

### 维度 4：同一个策划同一时段任务性质是否均衡

> 都是验收没有设计浪费脑力，都是设计没有落地就容易没交付

**PmSystem 能扫的**：
- `WorkItem.stage` 或 `Feature.stage` 分布
- 或 `design_landing` 阶段反推：what/how（设计）→ build（落地）→ make（验收）

**问题**：`stage` 字段填写质量如何？如果填得随意，用 `design_landing` 反推更可靠。

**阿茶输出（样例）**：
> "脑力结构预警：张三本周 4 条 WorkItem 均处于 what/how 阶段（纯设计），无 build/make。模式：'只设计不落地'。风险：下周交付空窗，或设计过度压缩落地时间。建议：搭配 1 条已进入 build 的 Feature，平衡产出节奏。"

**待讨论**：
- [ ] `stage` 字段质量：策划填得认真吗？如果不认真，阿茶统一用 `design_landing` 反推。
- [ ] 理想配比：设计:落地:验收 = ? 这个是否有团队约定？

## 六、PmSystem 深度理解（2026-04-26）

> 本节来源：通读 PmSystem 《使用手册》《AgentReadMe》后的关键洞察。直接影响阿茶拿数据的方式和报告口径。

### 6.1 Feature 不是策划的「每日待办」，是「版本交付物」

PmSystem 有两条独立工作线：
- **策划周计划** (`planner_work_items` / `#planner`)：本周/下周/未排期，策划的日常工作条目。
- **Feature** (`features`)：版本下的交付模块，「版本要出什么」。

**现状**：planner 连续返回空数组，说明策划团队没有养成填写周计划的习惯，或者从运营规划一键生成 Feature 后就不再维护周计划。

**对阿茶的意味**：当前从 Feature 反推策划工作安排是**退而求其次**的做法。数据口径是「版本交付物负责人」而不是「策划日常工作负责人」。策划周计划重新跑起来后，阿茶应切回 planner 作为主数据源。

### 6.2 Feature 状态流 & 交付检查

**状态流**：草稿 → 就绪(DoR通过) → 开发中 → 验收中(可选) → 测试中 → 已完成

**交付检查五维度** (`Feature.delivery`)：
- 代码交付：selfTest / codeReview / ownerAccept
- 资源交付：internalReview / integrated / deviceVisible / artQuality / taIntegration
- 内容交付：numbersConfirmed / experienceConfirmed / deviceVisible
- 性能兼容：perfSelfTest / assetBudget / deviceCompat
- 提测流程：ownerAccepted / pmApproved / qaReceived

**对阿茶的意味**：之前只看 `status`/`done`，会把「已做了但没点完成」误判为「未开始」。张颖的 4 个 P0 done=0，不等于什么都没做——可能已经在某个交付维度通过了。

**改进**：下版负荷图增加**交付完成度**栏位，区分「真空白」vs「没点完成」。

### 6.3 运营规划(OPS) 是 Feature 的上游工厂

**机制**：运营规划表格里的维度标签可以**「发送至版本」**，系统自动在该版本下创建同名 Feature，并填充优先级和分组。

**证据**：Feature 表里大量 `source="ops"`，`notes="来源: 运营规划 - xxx"`。

**对阿茶的意味**：
- 端午 17 条未分配 Feature，根源在**运营规划维度标签**上就可能没有 Owner。
- Feature 无 assignee 不等于「没人管」，可能是上游还没指派。
- 阿茶只读 Feature 表，看到的是**二手信息**。

**改进**：下一阶段开通 OPS 域数据读取，追溯未分配 Feature 在上游的状态。

### 6.4 Pipeline 节点 & Scope 锁定

**版本真实阶段**不是看 `phase` 字段，而是看 `pipeline_status` + `pipeline_ddls` + `scope_locked`。

- `phase` 字段常常**滞后**于实际工作。
- 五一版 `phase=planning`，但 pipeline 已经走到 dev，DDL 排到 4.28-4.29。
- `scope_locked=0` 说明版本还没锁定 Scope，理论上还在接收 Feature。

**对阿茶的意味**：之前报「五一版 release=4.22 已过期 4 天」是**错误解读**。`release_date` 是规划时的目标日期，实际发版日期要看 pipeline DDL 里的 releaseTesting/release。

**改进**：报告版本节点时，以 `pipeline_ddls`里的实际 DDL 为准，不以 `release_date` 为准。

### 6.5 插单 / 延期 / 转移

- **插单**：向已锁定 Scope 的版本推送内容 → Feature 标记 `is_rush=true`。
- **延期**：Feature 自动移动到下一个未发布版本，数据完整保留。
- **转移**：维度标签从版本 A 转到版本 B。

**对阿茶的意味**：Feature 的 `version_id` 可能在历史上变过。张颖 9 条全在五一版，可能是从更早版本延期过来的。延期意味着它们本来就是**「老债」**。

### 6.6 数据质量现状更新

| 数据项 | 现状 | 阿茶应对 |
|--------|------|---------|
| **策划周计划** | 连续多周返回空数组 | 不等待，**从版本 Feature 反向梳理**策划工作安排 |
| **工时估算** | 几乎全为 0 | **不依赖**，用 Feature 数量+分组+交付检查替代 |
| **Feature.assignee** | 有的填 ID、有的填中文名、有的空 | 已建立 ID→人名映射表，**但填写习惯不规范**需要治理 |
