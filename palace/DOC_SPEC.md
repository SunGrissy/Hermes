# 策划文档规范（Feature + 版本规划）

> 本规范定义策划文档（Feature 设计文档 + 版本内容规划）的分类、标注、结构要求。
> 目的：让审查系统正确理解文档意图，让下游团队快速定位"哪些能开工、哪些要等"。

---

## 一、文档分类

写文档之前，先确定两个属性：

### 1.1 文档类型（doc_type）

| 类型 | 什么时候用 | 典型例子 |
|---|---|---|
| **全新设计** | 从零搭建一套新系统/玩法 | 四象角力、锦标月赛 |
| **增量变体** | 在现有系统上做配置/参数调整 | 神君随心购礼包、节日限定礼包 |
| **运营活动** | 有时限的活动玩法 | 开火挑战、春节活动 |
| **紧急修复** | 线上问题的应急方案 | 崩溃修复、数值紧急调整 |

### 1.2 管线权重（pipeline_weight）

| 权重 | 判断标准 |
|---|---|
| **慢轨** | 需要新系统开发、跨多个团队协作、工期超过 2 周 |
| **快轨** | 复用现有系统、主要是配置/参数调整、工期 1 周内 |

**在文档开头标注这两项**：

```markdown
---
文档类型: 增量变体
管线权重: 快轨
基础系统: MasterUnlockPack 礼包框架
---
```

## 二、标注协议

文档中的每一个决策点、参数值、设计参考，都应该用标注标签表明其状态。
标签写在相关内容**前面**，用方括号包裹。

### 六个标签

| 标签 | 含义 | 怎么用 |
|---|---|---|
| `[已定]` | 已经确认的最终方案 | 附上决策依据或决策人 |
| `[待定·责任人·截止日]` | 还没确认，等某人拍板 | 必须写清楚谁负责、什么时候确认 |
| `[参考]` | 竞品或灵感参考，不是我们的方案 | 下游不要当作需求来执行 |
| `[数值·待标定]` | 方向确定，具体数值后续由数值组填入 | 写明数值的安全范围和标定方向 |
| `[约束]` | 下游必须遵守的硬性限制 | 说明约束来源（技术/法务/运营） |
| `[示意]` | 仅为说明意图，下游可以重新设计 | UX/前端看到这个标签就知道有自由度 |

### 使用示例

```markdown
### 抽奖概率

[已定] 基础概率分布如下（经数值组评审 2026-02-28，决策人：徐一卜）：
- 普通奖品：70%
- 稀有奖品：25%
- 传说奖品：5%

[数值·待标定] 保底机制触发次数，安全范围 30-50 次，由数值组根据经济模型确定。

[参考] MonopolyGo 的 sticker pack 采用类似阶梯概率，我们的方向略有不同。
```

```markdown
### 界面布局

[示意] 主界面参考下图，核心信息层级为：剩余次数 > 奖池预览 > 抽奖按钮。
具体视觉和交互方案由 UX 团队设计。

[约束] 抽奖动效时长不超过 3 秒（技术限制：帧率要求）。
```

### 扩展标签（跨层、竞品、收敛场景）

| 标签 | 含义 | 怎么用 |
|---|---|---|
| `[已采纳·来源]` | 从竞品/参考中采纳并调整 | 说明借鉴了什么、做了什么改动 |
| `[确定方案]` | 布局/流程已定，下游在此基础优化 | 与 `[示意]` 互斥：这个是定了的 |
| `[业务规格]` | WHAT 层涉及 BUILD 逻辑时标注 | 告诉系统策划"这是业务规则，不是技术方案" |
| `[边界]` | 功能范围边界 | 下游不要越过此边界 |
| `[体验意图]` | 给 UX 的体验方向 | 不规定具体形式，只传递想让玩家感受到什么 |
| `[指标·待基线]` | 方向已定，目标值待数据团队标定 | 附标定责任人和影响 |
| `[配置·待确认]` | 配置项待确认 | 附责任人、截止日、对方案的影响 |
| `[连接点·待决策]` | 跨模块连接逻辑依赖某决策项 | 引用决策清单中的待定项 |

### `[数值·待标定]` 增强格式

当数值尚未确定时，除了标签本身，还应附带三要素：

```markdown
[数值·待标定·责任人·截止日] 描述，安全范围 X-Y，影响：XXX。
```

示例：`[数值·待标定·徐一卜·03/20] 放大系数，安全范围 1-5，影响火花计算公式。`

### 跨层标注规则

**章节级标记（推荐）**：当文档包含多个层级的内容时，在章节标题中标注所属层级，方便审查系统和下游团队快速识别：

```markdown
## [WHAT] 体验意图
## [WHAT] 决策清单
## [HOW] 交互方案参考      ← 标注 [HOW] 说明这是 HOW 层内容
## [BUILD] 系统架构参考    ← 标注 [BUILD] 说明这是 BUILD 层内容
```

层级标记不改变章节内容的约束力——标了 `[HOW]` 不代表可以跳过 WHAT 层审查，只是帮助审查系统精确定位各层内容的边界。未标注层级的章节默认按文档元数据（如 `文档类型: 全新设计`）推断。

**行内标注**：在跨层引用的具体内容处使用标签：
- 凡涉及 HOW 层内容（截图、流程图、线框），必须标注 `[示意]` 或 `[参考]`，并写明"具体由 UX 产出"
- 凡涉及 BUILD 层内容（算法、接口、性能参数），必须标注 `[业务规格]`，并写明"具体由系统策划/PLT 产出"
- 竞品截图/视频必须标注 `[参考·竞品名]` 或 `[已采纳·竞品名]`，未标注视为"约束级别不明"

### 不打标签会怎样？

审查系统会将未标注的内容默认视为**"未决策"**进行审查。
如果一个参数其实已经线下确认了但没打 `[已定]`，报告会标为"决策缺口"——这是误报。
打标签 = 减少报告噪音 = 你不用花时间解释"这个其实已经定了"。

未标注的竞品截图/视频，审查系统会触发"约束级别不明"提醒。

## 三、增量文档专用标签

当文档类型为"增量变体"时，额外使用以下标签说明与基础系统的关系：

| 标签 | 含义 | 示例 |
|---|---|---|
| `[复用·系统名]` | 直接复用现有系统，无需重新描述 | `[复用·MasterUnlockPack] 礼包框架沿用现有实现` |
| `[配置变更]` | 仅改配置/参数，不改代码逻辑 | `[配置变更] 概率从 70/25/5 调整为 60/30/10` |
| `[增量·说明]` | 在现有功能上新增的部分 | `[增量] 新增自选机制：玩家解锁后可选 3 件` |

标注了 `[复用]` 的部分，审查系统**不会要求你重写架构文档或接口定义**——只检查复用声明是否成立。

## 四、文档结构模板

### 4.1 全新设计（慢轨）

```markdown
---

管线权重: 慢轨
---

| 术语 | 定义 |
|---|---|
| XXX | 本文档中指… |
（涉及多套数值体系时，必须在此明确区分，如"赛事积分"vs"段位星数"）

## 体验意图（必填，位于文档前 1/3）
本功能的核心体验是让玩家感受到______。
（一句话定义核心情绪体验，不是功能描述）

## 功能范围
- 覆盖：…
- 不覆盖：…
- 与现有系统关系：[复用·系统名] / [增量] / 独立新建

## 体验目标（分层）
| 用户群 | 情绪目标 | 行为目标 | 设计边界 |
|--------|----------|----------|----------|
| 大R    | …        | …        | 防止…    |
| 中R    | …        | …        | 防止…    |
| 轻付费 | …        | …        | 防止…    |

## 内容结构
- 功能模块关系（图或等效描述）
- 循环逻辑（日/周/月循环及衔接）
- **关键连接点清单**（管线依赖视角）：
  - **设计意图**：厘清「上游要给我什么/做什么决策，我的下游在等我什么」。填表时自问：我负责的这部分，等谁、谁等我？等的是数据、接口，还是决策拍板？
  | 连接点 | 上游模块 | 下游模块 | 上游要提供/决策什么 | 下游在等什么 | 状态 |
  |--------|----------|----------|---------------------|--------------|------|
  | XXX    | A        | B        | （数据/接口/决策项） | （数据/接口/决策项） | [已定] / [连接点·待决策] |

## 成功指标
- 北极星指标：[已定] / [指标·待基线] 1 个核心指标
- 分层参与指标：每个消耗层级至少 1 行为 + 1 留存
- 健康度指标：至少 1 个（如分布合理性、流失率、烈度）

## 决策清单
| 决策项 | 状态 | 依据/责任人 | 阻塞下游 |
|--------|------|-------------|----------|
| XXX | [已定] | 理由… | — |
| YYY | [待定·张三·03/15] | | UX 主界面 |

## 交互需求输入（四要素）
1. **核心体验节奏**：[单日/单周期/全程] 时间线
2. **关键情绪节点**（至少 3 个）：
   | 时刻 | 预期情绪 | 触发机制 | UX 需放大 |
   |------|----------|----------|----------|
   | 首次进入 | 新鲜感 | … | … |
   | XXX | 仪式感 | … | … |
3. **信息优先级**：P0 … > P1 … > P2 …
   （如有特殊场景，补充场景下的优先级变化）
4. **约束与自由度**：
   - [约束] 硬性要求（来源：技术/法务/运营）
   - [示意] 可重新设计
   - [体验意图] 方向性要求，不限具体形式

## 数值框架
- **设计意图**：支撑本功能预期体验的「基础数值设定」（如排行榜烈度、结算周期、参与规模、奖励梯度等）。既要让非数值同事能快速理解「体验上大概长什么样」，也要让数值同事知道该填哪些维度。
- **推荐写法**：先写「体验级数值意图」（用自然语言描述节奏、烈度、规模等，非数值能懂），再按类型分块填参数表（节奏/周期、烈度/规模、经济/概率），每项标 [已定] 或 [数值·待标定·责任人·截止日] 并附安全范围与影响。
- 参数表示例分块：**节奏与周期**（结算周期、赛季长度、刷新频率）、**烈度与规模**（参与人数、排名档位、奖励梯度）、**经济与概率**（产出/消耗、概率、保底等）。

## 风险与约束

## [HOW] 交互方案参考（可选）
> 以下内容为 WHAT 阶段的参考性输入，具体交互方案由 UX 团队产出。
（如有线框图、流程图等参考材料可放在这里，统一标注 [示意] 或 [参考]）

## [BUILD] 系统方案参考（可选）
> 以下内容为 WHAT 阶段对 BUILD 层的业务规格输入，具体系统方案由系统策划/PLT 产出。
（如有架构示意、接口草案等可放在这里，统一标注 [业务规格]）
```

## 五、审查档位说明

你的文档提交审查后，系统会根据文档类型和管线权重自动选择审查档位：

| 你的文档 | 审查档位 | 审查重点 | 不会审的 |
|---|---|---|---|
| 版本规划 | **版本排布预审** | 组盘健康度、Feature WHAT 交代、跨 Feature 互补性 | 单个 Feature 的详细设计质量 |
| 全新设计 + 慢轨 | **全量审查** | WHAT/HOW/BUILD 完整性 | — |
| 增量变体 + 快轨 | **增量审查** | 差异描述、参数合理性、系统兼容性 | 架构文档、接口定义、完整动效设计 |
| 运营活动 | **活动审查** | 玩法完整性、数值合理性、体验闭环 | 系统架构（复用的部分） |
| 紧急修复 | **最小审查** | 影响范围、回滚方案 | 几乎所有常规项 |

**核心原则**：快轨不是"更松"，而是"重点不同"。

增量文档的审查更关心：
- 参数和数值是否完整、合理 → 这反而比全新设计**更严格**
- 与现有系统的兼容性 → 增量变更最大的风险是"改坏现有的"
- 业务目标是否清晰 → 做变体总要有个理由

增量文档的审查不关心：
- 完整的系统架构（你复用的，不需要重写）
- 完整的接口定义（现有的就行）
- 深度体验意图宣言（商业化标品的意图是自明的）

## 六、快速对照表

写完文档后，对照检查：

### 所有文档通用

- [ ] 文档开头标注了 `文档类型` 和 `管线权重`
- [ ] 关键决策都打了状态标签（`[已定]` / `[待定]` / `[参考]`）
- [ ] 有成功指标（怎么衡量这个功能做得好不好）
- [ ] 有决策清单（已定的附依据，待定的附责任人和时间）

### 全新设计额外检查

- [ ] 有术语表
- [ ] 有一句话体验意图声明
- [ ] 有分用户群的体验目标
- [ ] 有给 UX 的交互需求输入（节奏、情绪、优先级、约束）
- [ ] 内容结构覆盖了功能模块 + 循环逻辑 + 关键连接点（连接点建议含「上游要提供/决策什么」「下游在等什么」）

## 附录：为什么要这样做？

### 问题 1："我线下都确认过了，为什么报告说缺失？"

因为审查系统只能看到文档，看不到你的线下对话。
打 `[已定]` 标签 = 告诉系统"这个已经确认了"，报告就不会误报。

### 问题 2："快轨需求为什么要写这么多？"

不需要。增量变体只要写差异部分。
但如果不标注 `[复用]`，系统不知道你用的是现有架构，就会问你"架构在哪？"。
标注清楚 = 审查更精准 = 你收到的报告更短。

### 问题 3："标签太多记不住怎么办？"

日常最常用的只有四个：`[已定]`、`[待定·人·日期]`、`[参考]`、`[示意]`。
先用这四个就够了。其他的遇到再查。

### 问题 4："版本规划也需要这么正式？"

版本规划是所有 Feature 的上游输入。Feature Owner 靠版本规划理解自己的"命题"。
如果版本规划只有标题和时间表，下游拿到的就是"裸命题"——要么猜要么反复确认。
填写体验意图和版本角色 = 下游直接开始设计 = 节省往返沟通时间。
