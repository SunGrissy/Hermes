# Feature 文档规范

> 本规范定义策划 Feature 文档的分类、标注、结构要求。
> 目的：让审查系统正确理解文档意图，让下游团队快速定位"哪些能开工、哪些要等"。

---

## 一、文档分类

写文档之前，先确定两个属性：

### 1.1 文档类型（doc_type）

| 类型 | 什么时候用 | 典型例子 |
|---|---|---|
| **全新设计** | 从零搭建一套新系统/玩法 | 四象角力、锦标月赛 |
| **增量变体** | 在现有系统上做配置/参数调整 | 神君随心购礼包、节日限定礼包 |
| **运营活动** | 有时限的活动玩法 | 开火挑战、春节活动 |
| **紧急修复** | 线上问题的应急方案 | 崩溃修复、数值紧急调整 |

### 1.2 管线权重（pipeline_weight）

| 权重 | 判断标准 |
|---|---|
| **慢轨** | 需要新系统开发、跨多个团队协作、工期超过 2 周 |
| **快轨** | 复用现有系统、主要是配置/参数调整、工期 1 周内 |

**在文档开头标注这两项**：

```markdown
---
文档类型: 增量变体
管线权重: 快轨
基础系统: MasterUnlockPack 礼包框架
---
```

---

## 二、标注协议

文档中的每一个决策点、参数值、设计参考，都应该用标注标签表明其状态。
标签写在相关内容**前面**，用方括号包裹。

### 六个标签

| 标签 | 含义 | 怎么用 |
|---|---|---|
| `[已定]` | 已经确认的最终方案 | 附上决策依据或决策人 |
| `[待定·责任人·截止日]` | 还没确认，等某人拍板 | 必须写清楚谁负责、什么时候确认 |
| `[参考]` | 竞品或灵感参考，不是我们的方案 | 下游不要当作需求来执行 |
| `[数值·待标定]` | 方向确定，具体数值后续由数值组填入 | 写明数值的安全范围和标定方向 |
| `[约束]` | 下游必须遵守的硬性限制 | 说明约束来源（技术/法务/运营） |
| `[示意]` | 仅为说明意图，下游可以重新设计 | UX/前端看到这个标签就知道有自由度 |

### 使用示例

```markdown
### 抽奖概率

[已定] 基础概率分布如下（经数值组评审 2026-02-28，决策人：徐一卜）：
- 普通奖品：70%
- 稀有奖品：25%
- 传说奖品：5%

[数值·待标定] 保底机制触发次数，安全范围 30-50 次，由数值组根据经济模型确定。

[参考] MonopolyGo 的 sticker pack 采用类似阶梯概率，我们的方向略有不同。
```

```markdown
### 界面布局

[示意] 主界面参考下图，核心信息层级为：剩余次数 > 奖池预览 > 抽奖按钮。
具体视觉和交互方案由 UX 团队设计。

[约束] 抽奖动效时长不超过 3 秒（技术限制：帧率要求）。
```

### 不打标签会怎样？

审查系统会将未标注的内容默认视为**"未决策"**进行审查。
如果一个参数其实已经线下确认了但没打 `[已定]`，报告会标为"决策缺口"——这是误报。
打标签 = 减少报告噪音 = 你不用花时间解释"这个其实已经定了"。

## 三、增量文档专用标签

当文档类型为"增量变体"时，额外使用以下标签说明与基础系统的关系：

| 标签 | 含义 | 示例 |
|---|---|---|
| `[复用·系统名]` | 直接复用现有系统，无需重新描述 | `[复用·MasterUnlockPack] 礼包框架沿用现有实现` |
| `[配置变更]` | 仅改配置/参数，不改代码逻辑 | `[配置变更] 概率从 70/25/5 调整为 60/30/10` |
| `[增量·说明]` | 在现有功能上新增的部分 | `[增量] 新增自选机制：玩家解锁后可选 3 件` |

标注了 `[复用]` 的部分，审查系统**不会要求你重写架构文档或接口定义**——只检查复用声明是否成立。

## 四、文档结构模板

### 4.1 全新设计（慢轨）

```markdown
---
文档类型: 全新设计
管线权重: 慢轨
---

# 功能名称

## 术语表
| 术语 | 定义 |
|---|---|
| XXX | 本文档中指… |

## 体验意图
（一句话：这个功能要让玩家感受到什么？）

## 体验目标
（分用户群描述各自的情绪/行为目标）

## 内容结构
（功能模块 + 循环逻辑 + 关键连接点）

## 成功指标
- 北极星指标：
- 参与指标：
- 健康度指标：

## 决策清单
| 决策项 | 状态 | 依据/责任人 |
|---|---|---|
| XXX | [已定] | 理由… |
| YYY | [待定·张三·03/15] | |

## 交互需求输入
（给下游 UX 的设计输入）
- 核心体验节奏：
- 关键情绪节点：
- 信息优先级：
- [约束] …
- [示意] …

## 数值框架
（经济模型、概率、成本收益）

## 风险与约束
```

### 4.2 增量变体（快轨）

```markdown
---
文档类型: 增量变体
管线权重: 快轨
基础系统: （填写复用的系统名）
---

# 功能名称

## 基础系统
[复用·系统名] 简述复用了什么，一两句话即可。

## 本次变更
（只描述与基础系统不同的部分）
- [增量] …
- [配置变更] …
- [调整] …

## 业务目标
[已定] 为什么做这个变体，预期收益是什么。

## 参数配置
（定价、概率、数量等具体数值）

## 衔接风险
（新配置与现有系统的兼容性注意事项）

## 下游影响
- 前端：需要新 UI / 纯配置
- QA：测试重点
- 运维：上线注意事项
```

### 4.3 运营活动

```markdown
---
文档类型: 运营活动
管线权重: 快轨/慢轨
活动周期: 起止时间
---

# 活动名称

## 术语表

## 活动概述
（一段话说清楚玩法核心）

## 体验节奏
（玩家在活动周期内的参与节奏设计）

## 玩法规则
（完整规则描述，覆盖所有分支路径）

## 数值设计
（产出、消耗、概率、保底等）

## 成功指标

## 决策清单

## 交互需求输入
（给 UX 的设计输入）

## 与现有系统的关系
（活动是否依赖现有系统？哪些部分 [复用]？哪些 [增量]？）
```

## 五、审查档位说明

你的文档提交审查后，系统会根据文档类型和管线权重自动选择审查档位：

| 你的文档 | 审查档位 | 审查重点 | 不会审的 |
|---|---|---|---|
| 全新设计 + 慢轨 | **全量审查** | WHAT/HOW/BUILD 完整性 | — |
| 增量变体 + 快轨 | **增量审查** | 差异描述、参数合理性、系统兼容性 | 架构文档、接口定义、完整动效设计 |
| 运营活动 | **活动审查** | 玩法完整性、数值合理性、体验闭环 | 系统架构（复用的部分） |
| 紧急修复 | **最小审查** | 影响范围、回滚方案 | 几乎所有常规项 |

**核心原则**：快轨不是"更松"，而是"重点不同"。

增量文档的审查更关心：
- 参数和数值是否完整、合理 → 这反而比全新设计**更严格**
- 与现有系统的兼容性 → 增量变更最大的风险是"改坏现有的"
- 业务目标是否清晰 → 做变体总要有个理由

增量文档的审查不关心：
- 完整的系统架构（你复用的，不需要重写）
- 完整的接口定义（现有的就行）
- 深度体验意图宣言（商业化标品的意图是自明的）

## 六、快速对照表

写完文档后，对照检查：

### 所有文档通用

- [ ] 文档开头标注了 `文档类型` 和 `管线权重`
- [ ] 关键决策都打了状态标签（`[已定]` / `[待定]` / `[参考]`）
- [ ] 有成功指标（怎么衡量这个功能做得好不好）
- [ ] 有决策清单（已定的附依据，待定的附责任人和时间）

### 全新设计额外检查

- [ ] 有术语表
- [ ] 有一句话体验意图声明
- [ ] 有分用户群的体验目标
- [ ] 有给 UX 的交互需求输入（节奏、情绪、优先级、约束）
- [ ] 内容结构覆盖了功能模块 + 循环逻辑 + 关键连接点

### 增量变体额外检查

- [ ] 标注了基础系统（`[复用·系统名]`）
- [ ] 只写了差异部分，没有重复描述已有系统
- [ ] 参数/配置值完整（或标了 `[数值·待标定]` 附安全范围）
- [ ] 衔接风险有说明

### 运营活动额外检查

- [ ] 玩法规则覆盖了所有分支路径
- [ ] 数值设计完整（产出/消耗/概率/保底）
- [ ] 活动周期和节奏设计清楚

## 附录：为什么要这样做？

### 问题 1："我线下都确认过了，为什么报告说缺失？"

因为审查系统只能看到文档，看不到你的线下对话。
打 `[已定]` 标签 = 告诉系统"这个已经确认了"，报告就不会误报。

### 问题 2："快轨需求为什么要写这么多？"

不需要。增量变体只要写差异部分。
但如果不标注 `[复用]`，系统不知道你用的是现有架构，就会问你"架构在哪？"。
标注清楚 = 审查更精准 = 你收到的报告更短。

### 问题 3："标签太多记不住怎么办？"

日常最常用的只有三个：`[已定]`、`[待定·人·日期]`、`[参考]`。
先用这三个就够了。其他的遇到再查。
