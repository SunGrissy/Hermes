# Palace 设计方向备忘录

> 记录已确认的设计共识和架构演进方向，供后续迭代参考。

## 已实现（v0.4）

### 架构：两步流程（提取 → 评估）

v0.3 问题：四个角色并行审查 → 合并去重。去重靠字符串匹配，不可靠。报告按角色组织，不像"一份综合报告"。

v0.4 方案：
1. **提取步骤**（boundary 角色）：读文档，输出结构化 checklist（每个核心交付物的存在状态 + 提取原文 + 缺口描述）
2. **评估步骤**（PLD/PLE/PLT 并行）：拿着 checklist 逐项评估，给出影响判断 + 补充发现
3. **合成步骤**（代码）：将提取结果 + 各视角评估合并为按议题组织的报告数据

好处：
- **天然去重**：所有角色看同一份 checklist，不会产生重复
- **按议题组织**：报告围绕问题展开，不是围绕角色展开
- **渲染器无分析**：report.py 只做 JSON → Markdown 映射，零启发式

### Schema 合约

三组 schema 分别服务三个阶段：
- `EXTRACTION_SCHEMA`：boundary 角色输出格式（layer_overview + checklist + cross_layer_observations）
- `ROLE_ASSESSMENT_SCHEMA`：评估角色输出格式（verdict + issue_assessments + supplementary_findings）
- `REPORT_DATA`：合成结果格式（report.py 的输入合约）

字段设计原则：**不让 report.py 猜**——现状、目标状态、达标要求等全部由 LLM 直接输出或 synthesize 逻辑计算。

### Mixed-first 策略（继承自 v0.3）
- 所有场景默认处理混合层级文档
- boundary 角色 = "文档结构与连贯性教练"
- PLD/PLE/PLT persona 包含 mixed 文档感知
- 跨层审查三维度：P0 意图一致性、P1 下游就绪度、P2 标注清晰度

### 报告结构（v0.4）
- 标题场景驱动（"Feature 预审报告"）
- 文档分层概览（boundary 提取数据直接渲染）
- 裁决 + P0 行动表（目标状态导向）
- 审查详情按议题组织，每个议题下多视角评论自然穿插
- 跨层连贯性（意图传递 / 就绪度 / 标注建议）
- P1/P2 后续改进建议（统一表格格式）

### 废弃的设计
- `_guess_status` / `_guess_standard` / `_to_target_state`（启发式猜测 → 改为 LLM 直接输出）
- `_dedup` / `_kw_sim`（事后去重 → 改为源头统一 checklist）
- `_extract_layer_data`（关键词提取分层概览 → 改为 LLM 直接输出）
- `_collect_crosslayer`（关键词分类 → 改为 LLM 直接输出 category）
- `_sanitize_tone`（字符串替换换措辞 → 改为 prompt 层面要求中性语气）
- 角色分割式报告结构（按 PLD/PLE/PLT 区块展示 → 改为按议题展示）

## 后续迭代方向

### 方向 1：文档分类感知 + 审查档位（v0.5 核心）

**问题**：当前引擎对所有文档使用同一套 checklist，不区分文档类型和管线权重。
快轨增量文档（如在现有礼包系统上做配置变体）被审出 25 个问题、3 个阻断——大量假阳性。
策划线下已确认但文档中标了"待确认"的内容被误判为"未决策"——无法区分"决策缺口"和"记录缺口"。

#### 1.1 文档类型分类

输入元数据新增 `doc_type` 字段，联合 `pipeline_weight` 决定审查档位：

| doc_type | 适用场景 | 说明 |
|---|---|---|
| `full_spec` | 全新系统/玩法（慢轨） | 从零设计，需要完整 WHAT/HOW/BUILD |
| `delta` | 存量系统的变体/配置（快轨） | 只描述与基础系统的差异 |
| `campaign` | 运营活动 | 侧重玩法完整性和数值合理性 |
| `hotfix` | 紧急修复 | 最小审查：影响范围 + 回滚方案 |

#### 1.2 审查档位

| 档位 | 触发条件 | checklist 策略 | 严重程度映射 |
|---|---|---|---|
| **全量** | full_spec + 慢轨 | 完整 checklist | 标准映射 |
| **增量** | delta + 快轨 | 增量 checklist（差异描述 + 衔接风险 + 业务目标） | 体验意图 P0→P2，架构/接口跳过，参数完整性+兼容性升级为 P0 |
| **活动** | campaign | 活动 checklist（玩法闭环 + 数值合理性 + 体验节奏） | 数值和体验闭环为 P0 |
| **最小** | hotfix | 影响范围 + 回滚方案 | 仅 P0/P1 |

增量档位下同一检查项的严重程度与全量档位不同——快轨不是"更松"，而是"重点不同"：

| 检查项 | 全量（慢轨） | 增量（快轨） |
|---|---|---|
| 体验意图声明 | P0 阻断 | P2 建议 |
| 系统架构方案 | P0 阻断 | **跳过**（标注了复用系统即可） |
| 接口定义 | P1 必改 | **跳过** |
| 数值/参数完整性 | P1 必改 | **P0 阻断**（快轨核心就是参数配置） |
| 系统兼容性/衔接风险 | P1 必改 | **P0 阻断** |
| 术语表 | P1 必改 | P2 建议 |
| 业务目标/成功指标 | P0 阻断 | P0 阻断（保持不变） |

#### 1.3 实现方案

- `what_precheck.yaml` 拆分或参数化：根据 `doc_type + pipeline_weight` 选择 checklist 子集
- boundary.yaml 的 extraction prompt 注入档位信息，让 LLM 在提取时就知道哪些项可以跳过
- `_assign_severity` 根据档位查表映射，而非统一规则
- 报告头部明确标注档位："本次审查档位：增量（快轨），基于 delta 文档审查标准"

#### 1.4 增量文档的审查模型

delta 类型文档的核心 checklist：

| 检查维度 | 具体检查 |
|---|---|
| 基础系统声明 | 明确标注复用了哪个系统 |
| 差异点完整性 | 所有与基础系统不同的参数/流程是否说清楚 |
| 业务目标 | 为什么做这个变体、预期收益 |
| 衔接风险 | 新配置是否与现有系统兼容 |
| 下游影响 | 对前端/QA/运维有什么额外工作 |

**不检查的**：系统架构（已有）、接口定义（已有）、完整动效设计（复用）、体验意图宣言（商业化标品不需要）。

### 方向 2：标注协议（与方向 1 联动）

**问题**：策划文档中"待确认""参考""已拍板"等决策状态混杂，审查引擎无法区分"没做"和"做了但没记录"。

#### 2.1 六标签体系

| 标签 | 含义 | 引擎行为 |
|---|---|---|
| `[已定]` | 线下已确认，最终方案 | 不质疑决策本身，检查是否附了依据和决策人 |
| `[待定·责任人·截止日]` | 未决策 | 检查是否影响下游启动 |
| `[参考]` | 竞品/灵感参考，非约束 | 不作为缺失项处理 |
| `[数值·待标定]` | 方向确定，数值后续填入 | 检查有无标定方向和安全范围 |
| `[约束]` | 下游必须遵守的硬性要求 | 正常审查 |
| `[示意]` | 仅说明用途，下游可重新设计 | 不检查完整性 |

设计要点：
- 标签极简——策划愿意用才有用
- 不打标签 = 默认"未决策"审查——推动标注习惯的激励机制
- 标签本身即信息——下游看到 `[待定·数值·03/15]` 就知道等谁、等到什么时候

#### 2.2 引擎适配

extraction 角色识别标签后调整行为：
- `[已定]` 无依据 → 降级 P2："建议补充决策依据"
- `[待定·X·日期]` → 不标为"缺失"，改为"待定项已识别，关注是否阻塞下游"
- `[参考]` → 不计入完成度
- 无标注 → 按"未决策"处理，额外提示"建议补充状态标注"

#### 2.3 报告输出分层

阻断项拆为两类：
- **决策缺口**（真正 P0）：没人想过、没人拍板的问题
- **记录缺口**（P1 不阻断）：决策存在但文档没体现

这对策划的心理感受完全不同：前者是"帮我发现盲区"，后者是"提醒我补文档"。

#### 2.4 快轨文档专用标签

增量文档额外支持：
- `[复用·系统名]` — 复用现有系统，不需要重新描述架构
- `[配置变更]` — 仅配置调整，无代码变更
- `[增量]` — 在现有功能基础上的增量变化

### 方向 3：审查在管线中的角色定位

审查不是关卡，而是**信息对齐加速器**：

| 面向 | 审查的价值 |
|---|---|
| 上游（策划/Owner） | 帮你检查"脑子里的东西是否都落到纸上"，减少下游反复确认 |
| 下游（UX/系统/前端） | 帮你快速识别"哪些可以开工、哪些要等、等谁" |
| 管线（PLD/PMO） | 帮你判断"Feature 当前卡在什么位置、谁是瓶颈" |

当报告能在每个待定项旁标出 `待定·责任人·预计时间` 时，审查报告同时变成项目管理工具。

### 方向 4：checklist 模板外置

当前核心交付物清单写在 boundary.yaml persona 里。可独立为 YAML/JSON 配置：
- 按 doc_type 组织不同 checklist
- 支持项目组自定义"WHAT 层应该有什么"
- 与审查档位联动：delta 文档自动加载增量 checklist

### 方向 5：完成度 checklist 替代三档裁决

当前仍保留 block/concern/pass 三档。目标：每层完成度百分比 + 缺口清单。

### 方向 6：LLM 提取可信度

提取步骤可能漏项或误判。后续可加：
- 提取结果的 confidence score
- 多次提取取交集
- 人工确认环节

### 方向 7：HTML 报告 + 内联校准（已设计，待实现）

**问题**：制作人校准 AI 判断时需要在报告和反馈工具之间切换，打断阅读节奏。

**方案**：报告渲染为单页 HTML（自包含，无外部依赖），支持内联批注：

1. **阅读态**：与 Markdown 报告等效的排版，每条角色评论右侧有 📝 图标
2. **批注态**：点击 📝 展开行内输入框，填写校准意见（如"MonopolyGo验证了类似结构，不应一刀切"）
3. **持久化**：批注自动保存到 localStorage；页面底部"导出校准"按钮输出 JSON
4. **学习入口**：`py run.py learn report.html`（或导出的 JSON）→ 解析批注 → 写入 `calibrations/lessons.yaml`
5. **注入闭环**：后续审查时 engine.py 加载 lessons.yaml，将校准经验注入对应角色的 system prompt

**交互要求**：
- 零安装：纯静态 HTML + 内嵌 JS/CSS
- 批注不改变报告原文（DOM 追加而非替换）
- 导出 JSON 包含：issue_id、role_perspective、original_comment、user_correction、timestamp
- lessons.yaml 按角色分组存储，支持累积而非覆盖

### 方向 8：WHAT 交互需求输入质量（v0.4 已实现）

boundary.yaml WHAT 层核心交付新增"交互需求输入"维度，评估 WHAT 文档给下游 UX 的设计输入是否充分。四个必备要素：
1. 核心体验节奏意图
2. 关键情绪节点
3. 信息优先级提示
4. 约束与自由度

### 方向 9：文档结构合规性（v0.4 已实现）

新增三项结构性检查：术语表、管线权重标注、功能范围声明。混合文档尤其需要术语表防止同一词汇在不同上下文中被误解。

### 方向 10：审查驱动文档规范沉淀

通过 mixed 文档审查积累案例 → 提取共性缺口 → 沉淀为文档规范（见 `DOC_SPEC.md`）→ 反哺审查维度。
已产出初版策划文档规范，包含标注协议和分类模板。
